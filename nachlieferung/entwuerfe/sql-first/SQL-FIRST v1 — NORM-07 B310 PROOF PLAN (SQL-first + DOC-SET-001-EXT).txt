N-07.1 Ausgangslage: DOC-SET-001 existiert, aber muss erweitert werden
================================================================================
DOC-SET-001 (B310) beweist bereits:
- No Magic Numbers für Timer/TTL/Grace (grep Gate)
- Key References sollen im settings_catalog vorhanden sein (Ansatz)

Problem (Gap):
- DOC-SET-001 ist “Timer-fokussiert”. SQL-first braucht zusätzlich:
  a) Non-Time Keys Harvest (Bandbreite, Quota, Ports, toggles, limits)
  b) Alias/Prefix Cross-Check
  c) Key-Set Completeness pro PH

================================================================================
N-07.2 DOC-SET-001-EXT (Delta-Beschreibung)
================================================================================
Ziel:
- Dokumentenweit beweisen: “Alle policy keys sind im catalog”, nicht nur Timer.

Delta (in B310, Abschnitt DOC-SET-001):
- Ergänze Search-Gate um:
  (1) Non-Time Key Harvest:
      - Suchmuster für “*_bps”, “*_bytes”, “*_pct”, “*_limit”, “*_quota”, “*_concurrency”, “*_port”
      - Expected: Treffer nur als settings_* key references, niemals als Hardcoded Zahlen.
  (2) Prefix/Alias Cross-Check:
      - Jede Key-Referenz muss einem erlaubten Prefix entsprechen (NORM-02)
      - Deprecated aliases dürfen nur in alias table vorkommen, nicht in Consumers.
  (3) Required-Key-Set Cross-Check:
      - Für jede Phase: Required-Key-Set (NORM-06) muss vollständig im catalog sein.
      - Jede Consumer-Key-Referenz muss in mindestens einem Key-Set auftauchen (oder als optional_key gelistet sein).

Validierung:
- Test schlägt fehl, wenn:
  - Consumer referenziert key, der nicht im catalog existiert,
  - Consumer referenziert key ohne erlaubten prefix,
  - Consumer enthält deprecated alias reference,
  - Consumer enthält Hardcoded “policy numbers”.

N-07.3 Neue B310 Proofs (SQL-first Kern)
================================================================================
Diese Proofs ergänzen B310 (als neue Test-IDs oder Untertests):

B310-SQLF-CAT-001 (Completeness):
- Ziel: Alle required keys existieren im settings_catalog.
- Delta: Erzeuge Liste “required keys” aus NORM-06 Entries (pro Phase).
- Expected: 0 missing.

B310-SQLF-CAT-002 (Validation):
- Ziel: Typ/Range/enum validations greifen, invalid -> INVALID state.
- Expected: invalid values erzeugen reason_code (NORM-04) + /diag drift flag.

B310-SQLF-ALIAS-001 (Alias determinism):
- Ziel: alias resolves deterministically to canonical; removed rejects.
- Expected: alias_used flagged, deprecated triggers drift flag.

B310-SQLF-ALIAS-002 (Deprecated/Removed alias behavior):
- Ziel: Deprecated aliases sind nur noch als Alias zulässig; Removed aliases werden deterministisch rejected.
- Expected: Deprecated alias -> drift flag + reason_code (NORM-04); Removed alias -> reject + reason_code (NORM-04).

B310-SQLF-RES-001 (Resolution precedence):
- Ziel: Effective precedence ist deterministisch: CONNECTION > CUSTOMER > GLOBAL.
- Expected: effective_source korrekt (NORM-05 trace), kein “silent fallback” gegen die Precedence.

B310-SQLF-RES-002 (Key-state correctness):
- Ziel: key_state korrekt: MISSING/INVALID/OK (NORM-05) anhand catalog + validations.
- Expected: state + reason_code konsistent (NORM-04), drift_flags konsistent (NORM-03/07).

B310-SQLF-DRIFT-001 (Settings Drift flags):
- Ziel: Drift-Flags korrekt gesetzt (catalog/value/alias/reference mismatch).
- Expected: /diag shows DRIFT_* and reason_code.

B310-DIAG-SQLF-001 (Diag exposure):
- Ziel: /diag exposes db_state + settings health + (admin) settings_trace.
- Expected: scope-limited, size-limited, no PII.

B310-DIAG-SQLF-002 (Trace scope + size limits):
- Ziel: settings_trace ist admin-only, scope-limited und size-limited (kein “full dump”, keine PII).
- Expected: Trace liefert nur Contract-Felder aus NORM-05; Überschreitungen werden verhindert/abgeschnitten (ohne Sensitive Leaks).

B310-DIAG-SQLF-003 (drift_flags correctness):
- Ziel: drift_flags korrekt für Missing/Invalid/Alias/Reference-Mismatch Szenarien.
- Expected: drift_flags + reason_code konsistent (NORM-03 + NORM-04) und im /diag nachvollziehbar.

B310-DIAG-SQLF-004 (B270 non-breaking / additive-only):
- Ziel: /diag Erweiterung bleibt strikt additiv; keine Umbenennung/Entfernung bestehender B270 Felder.
- Expected: Bestehende /diag Felder bleiben stabil; SQL-first ergänzt nur backend.* Subobjekte (NORM-05).

SQLF-KH PROOF-GRUPPE (Key-Harvest v1: 8 Keys) — Ableitung
================================================================================
ZIEL:
- Beweist, dass die 8 Harvest-Keys contract-geschlossen sind: presence + validation + alias + expected-fail + diag-trace.

INPUT:
- SQLF-HARVEST-01 (Key-Harvest v1)
- SQLF-CATADD-01 (Katalog-Aufnahme-Spezifikation v1)
- NORM-01/02/04/05

PROOF-IDS (ENTWURF, B310):
- B310-SQLF-KH-001: Catalog Presence
  • Ziel: alle 8 Canonical Keys existieren in settings_catalog.
  • Validierung: DOC-SET-001-EXT Cross-Check meldet 0× missing catalog keys.
  • Expected Fail: KEY_MISSING → reason_code=R_CONFIG_CATALOG_MISSING (NORM-04 EXT-SQLF-001); /diag summary: backend.settings.completeness=false; admin trace: backend.settings_trace[*].key_state=MISSING (NORM-05).

- B310-SQLF-KH-002: Value Validation + Constraints
  • Ziel: Constraints werden erzwungen (Range, Relation red<green, bytes>=min).
  • Validierung: negative tests → Expected Fail.
  • Expected Fail: VALUE_INVALID → reason_code=R_CONFIG_KEY_INVALID (NORM-04 EXT-SQLF-003); /diag zeigt Expected-Fail über key_state=INVALID (NORM-05 trace) + drift_flags (NORM-03).

- B310-SQLF-KH-003: Alias Resolution (Legacy → Canonical)
  • Ziel: Legacy Keys funktionieren nur als Alias, Canonical bleibt Truth.
  • Validierung: Alias gesetzt → trace source=alias, alias_used=true.
  • Expected Fail: Alias-Map fehlt → reason_code=R_CONFIG_ALIAS_MAP_MISSING (EXT REQUIRED in NORM-04); Gate CI-003.

- B310-SQLF-KH-004: Tighten-only Fallback (Disk-Safety)
  • Ziel: Bei missing/invalid darf fallback niemals loosening sein.
  • Validierung: forced-missing/invalid → effective_value <= default_cap/retention.
  • Expected Fail: Violation → reason_code=R_CONFIG_FAILCLASS_VIOLATION (EXT REQUIRED in NORM-04); Gate CI-005.

- B310-SQLF-KH-005: /diag Trace Completeness
  • Ziel: /diag liefert für jeden dieser 8 Keys: effective_value + source + reasons + last_refresh_age.
  • Validierung: Schema-Check in DOC-SET-001-EXT.
  • Expected Fail: Feld fehlt → reason_code=R_DIAG_CONTRACT_BREACH (EXT REQUIRED in NORM-04); Gate CI-001.

CI/GATE ZUORDNUNG (ENTWURF):
- CI-001: Contract/Schema (diag + catalog mandatory fields) → KH-001, KH-005
- CI-003: Alias/Mapping Completeness → KH-003
- CI-004: Range Validation Gate → KH-002 (optional, wenn CI-004 existiert)
- CI-005: Safety/Tighten-only Enforcement → KH-004
