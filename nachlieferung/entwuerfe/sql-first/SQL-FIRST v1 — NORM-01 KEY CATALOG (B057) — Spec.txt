================================================================================
N-01.1 Begriffe
================================================================================
- “Key” = policy-relevanter Parametername, eindeutig (canonical name), stable.
- “Catalog” = settings_catalog: Definitionen + Validatoren + Fail-Class.
- “Scoped Value Tables”:
  • settings_global      (Default/Baseline)
  • settings_customer    (Override pro Kunde/Account)
  • settings_connection  (Override pro vpn_connection / Subaccount)

================================================================================
N-01.2 Scope-Modell (MUST)
================================================================================
MUST Scopes (wie B057):
- GLOBAL:     genau 1 Wert pro key (Baseline)
- CUSTOMER:   genau 0..1 Wert pro (customer_id, key)
- CONNECTION: genau 0..1 Wert pro (vpn_connection_id, key)

Override-Whitelist:
- Ein Key MUSS im Katalog definieren, welche Scopes überhaupt überschreiben dürfen.
- Override für nicht-overridebaren Key => Hard Fail + Audit-Event (B057).

================================================================================
N-01.3 settings_catalog Contract (MUST)
================================================================================
Jeder Key im settings_catalog muss mindestens enthalten:

(1) Identität
- key (canonical, stable, unique)
- key_family (z.B. vpn_qos_, peak_profile_, dns_force_, log_retention_)
- key_prefix (Namespace: web_/vpn_/peak_/radius_/settings_/log_/spool_)

(2) Typ/Constraints (Validation ist Pflicht)
- value_type (bool/int/float/string/enum/json)
- constraints:
  - min/max (numerisch)
  - allowed_values (enum)
  - regex/pattern (string)
  - json_schema (wenn json)
- unit (z.B. seconds, ms, bps, bytes, pct)

(3) Mutability / Safety
- mutability_class: immutable | admin_only | customer_allowed
- change_guard: tighten_only | allow_loosen | deny_changes_while_active
  (Hinweis: genaue Semantik wird pro Domain im Consumer-Contract konkretisiert, aber der Katalog muss
   mindestens markieren, ob loosening grundsätzlich erlaubt ist.)

(4) Override-Regel
- allowed_override_scopes: subset of GLOBAL/CUSTOMER/CONNECTION
- precedence_order ist fix: CONNECTION > CUSTOMER > GLOBAL

(5) Fail-Class (Policy-Verhalten bei Missing/Invalid/DB_UNKNOWN)
- fail_class: fail_closed | fallback_baseline | fallback_last_known | tighten_only
- expected_reason_code_on_fail: Reason Registry (NORM-04)

(6) Dokumentation / Panel-Text (PFLICHT)
- title_short (1 Zeile)
- description (Meaning/Impact)
- examples (optional, aber empfohlen)
- linked_consumers (Liste: welche Domains/Blöcke konsumieren)

================================================================================
N-01.4 Key State Machine (MUST, für jedes Effective-Resolution Ergebnis)
================================================================================
Für jeden konsumierten Key muss der Resolver (normativ NORM-02) eine key_state liefern:

- OK: value valid, effective_value derived, effective_source known.
- MISSING: required key fehlt im gewählten Scope UND kein zulässiger Fallback existiert.
- INVALID: value vorhanden, aber verletzt value_type/constraints.
- FALLBACK_ACTIVE: value invalid/missing, aber Fail-Class erlaubt definierten fallback; fallback wurde genutzt.
- DB_UNKNOWN: Datenquelle nicht verlässlich (DB_DOWN/timeout/consistency fail) => Fail-Class entscheidet.

================================================================================
N-01.5 SQL-first Magic-Guard (MUST)
================================================================================
- Kein Consumer darf stille Defaults verwenden.
- Wenn ein Consumer einen Parameter braucht, muss er als Key im catalog existieren
  und in den Required-Key-Sets (NORM-06) der Phase auftauchen.
- DOC-SET-001-EXT (später Gate) muss “Consumer referenced key not in catalog” als Failure markieren.

================================================================================
N-01.6 Validierung (DoD, referenziert B310)
================================================================================

- B310-SQLF-CAT-001: “Alle required keys existieren im catalog” (completeness)
