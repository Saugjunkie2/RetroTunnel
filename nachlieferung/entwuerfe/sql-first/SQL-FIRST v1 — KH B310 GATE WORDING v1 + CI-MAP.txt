================================================================================

B310-SQLF-KH-006 (BOUNDS VALIDATION GATE)
-----------------------------------------
Gate-Name (CI): CI-SQLF-KH-006-BOUNDS
Scope:
- Canonical Keys:
  • web_ip_pool_green_threshold
  • web_ip_pool_red_threshold
  • web_settings_cache_ttl_seconds
  • web_log_detailed_retention_days
  • web_log_detailed_max_total_bytes
  • web_log_aggregate_retention_months
  • web_spool_retention_days
  • web_spool_max_total_bytes

Requirement (MUST PASS):
- Für jeden Key existiert /diag trace (DIAG-KH-TRACE-001).
- validation_state muss unter Normalwerten OK sein.
- Bei absichtlich injizierten invalid inputs muss:
  • validation_state=INVALID (oder RELATION_INVALID für relation cases)
  • effective_value muss SAFE sein (DEFAULT/FALLBACK oder CAPPED), niemals “invalid passthrough”.

Fail Conditions (MUST FAIL CI):
- missing trace for any key
- invalid passthrough: effective_value == invalid input
- unbounded: effective_value fehlt/None wo numeric required ist
- source undefined / validation_state missing

Proof Inputs (Expected-Fail suite):
- KH-EXFAIL-010/011/020/021/041 (siehe SQLF-KH-EXFAIL-01)

B310-SQLF-KH-007 (RELATION red<green GATE)
-----------------------------------------
Gate-Name (CI): CI-SQLF-KH-007-RELATION
Requirement (MUST PASS):
- Relation: web_ip_pool_red_threshold < web_ip_pool_green_threshold
- Bei injiziertem red >= green muss:
  • validation_state=INVALID (oder RELATION_INVALID)
  • reasons include reason_class SETTINGS_RELATION
  • /diag trace exists for BOTH keys and flags the relation failure.

Fail Conditions (MUST FAIL CI):
- relation violation does NOT trigger invalid
- only one key shows relation failure
- missing reason_class SETTINGS_RELATION

Proof Inputs:
- KH-EXFAIL-030

B310-SQLF-KH-008 (CAP / TIGHTEN-ONLY SAFETY GATE)
-------------------------------------------------
Gate-Name (CI): CI-SQLF-KH-008-CAP-SAFETY
Interpretation:
- Dieser Gate ist nur “hart” CI-fähig unter DET-REC-01 Lock:
  • strict-fail + safe fallback
  • cap active for budget keys

Requirement (MUST PASS) under DET-REC-01:
- Für Budget/TTL Keys (siehe DET-REC-01):
  • wenn SQL value > cap → effective_value=cap_value
  • source=CAPPED und reasons include SETTINGS_CAPPED
- Bei invalid budgets (0/neg/overflow):
  • validation_state=INVALID
  • effective_value SAFE (DEFAULT/FALLBACK oder CAPPED)
- “tighten-only” invariant:
  • effective_value darf nie “looser” sein als baseline safe bounds
  (hier muss in späterer Norm definiert sein, was “looser” exakt heißt; Gate prüft mindestens: not unlimited/not higher than cap)

Fail Conditions (MUST FAIL CI):
- cap not applied when over cap
- missing CAPPED source when cap applied
- invalid budgets lead to unlimited/no-limit effective behaviour
- missing reasons class SETTINGS_CAPPED on cap events

Proof Inputs:
- KH-EXFAIL-011/040/041

================================================================================
H) KH-008 ASSERTIONS (SB-aware) — Contract-Closed
================================================================================
Unter der Annahme, dass SB-Model FIX ist (DEC-SQLF-KH-SB-001; Recommended MODEL_1 via SQLF-KH-SB-FIXAPPLY-01):

Für Keys aus B1–B3 (Budget/Retention/TTL):
H1) INVALID/MISSING tighten-only:
- Wenn validation_state != OK:
  • assert effective_value <= safe_baseline_value
  • assert safe_baseline_value ist gesetzt (numeric, finite)

H2) CAP tighten-only:
- Wenn source == CAPPED oder reasons include SETTINGS_CAPPED:
  • assert effective_value <= cap_value (wenn cap_value als Feld existiert)
  • mindestens: effective_value <= safe_baseline_value
  • assert source == CAPPED (Consistency)

H3) No-Unbounded:
- In allen Fällen:
  • effective_value muss numeric & finite sein (>=1) und darf nicht als “unlimited sentinel” durchrutschen.

Hinweis:
- cap_value Feld ist optional in v1; wenn nicht vorhanden, bleibt der Gate-Check auf EV<=SB + source/reasons.
