----------------------------------------------------------------------
2) Begriffe / Normalformen
----------------------------------------------------------------------

- canonical_key:
  - Der einzige “Soll”-Name eines Keys (lower_snake_case, prefix allowlist).
- alias_key:
  - Legacy-/Übergangsnamen, die gelesen werden dürfen (Write verboten), inkl. dot-keys (nur MIGRATION_REQUIRED).
- rename:
  - Soll-Migration: alias/alt → canonical (vNext).
- keyset:
  - Gruppierung von keys als Minimum Contract pro Phase (PH1/PH2 etc.).

----------------------------------------------------------------------
3) Datensatz-Schema (pro Key) — Normiertes Inventarformat
----------------------------------------------------------------------

Jeder Key-Eintrag muss dieses Schema tragen (auch wenn einzelne Felder leer bleiben dürfen):

KEY:
  canonical_key: <string>
  alias_keys: [<string>, ...]
  deprecated_alias_keys: [<string>, ...]          # optional; falls klar getrennt
  datatype: <enum>                                # z.B. INT|BOOL|STRING|JSON|IPV4|CIDR|...
  unit: <string|null>                             # z.B. seconds|days|bps|count|...
  # Hinweis: datatype/unit dürfen in frühen PH-Ständen "derived" sein (aus Key-Name/Contract),
  # müssen aber später durch kanonische Meta (Harvest/Norm) bestätigt werden; ansonsten REG_DRIFT.
  constraints:
    range: <min..max|null>
    regex: <pattern|null>
    enum: [<v>, ...]                              # optional
  default_policy:
    value: <literal|null>                         # nur wenn im Harvest explizit
    source: <HARVEST-ID|null>                     # optional
  fail_policy:
    class: <enum|null>                            # FAIL_CLOSED|SAFE_DEFAULT|WARN_ONLY|TIGHTEN_ONLY|MIGRATION_REQUIRED|CONFLICT
    reason_tokens: [<REG_REASON_*>, ...]          # optional, wenn bereits normiert
  consumer_domains: [<PHx|module>, ...]           # z.B. PH1, PH2, peak, radius, webpanel, daemon
  writer_policy_ref:
    doc: DOC-SET-WRITEPATH
    rule: <id|null>                               # optional pointer
  keysets: [<KSET-ID>, ...]                       # z.B. PH1-K01.., PH1-REQ-SET-01 etc.
  notes: <string|null>                            # nur technisch/normativ, keine Story

----------------------------------------------------------------------
4) Katalog-Struktur (befüllt aus Harvest; ohne Chatverlauf-Abhängigkeit)
----------------------------------------------------------------------

4) Katalog-Struktur (befüllt aus Harvest; ohne Chatverlauf-Abhängigkeit)

Diese Datei ist ein **Inventar** der kanonischen SQL-Settings-Keys (inkl. Legacy-Alias/Rename).
Ziel: **Drift-freie, eindeutige Benennung** + nachvollziehbare Konsolidation.

Pro Key-Eintrag werden (mindestens) geführt:
- canonical_key_id: stabiler Identifier (z.B. PH1-Kxx oder KEY_<UPPER>)
- canonical_key: der kanonische Key-Name
- allow_prefix: Prefix-Regel (PR-PFX Allowlist)
- alias_keys: bekannte Legacy-/Alias-Keys (falls vorhanden)
- keysets: Zugehörigkeit zu KSETs (falls bekannt)
- notes: Freitext (z.B. Quelle/Status)

Hinweis:
- Dieses Inventar darf **Stub-Einträge** enthalten (nur Namen/Beziehungen), wenn Metadaten (Typ/Unit/Range/Default/Fail-Policy) noch nicht explizit kanonisiert wurden.
- Alias/Rename-Beziehungen stammen aus HARVEST-Indices (v1/v2) bzw. kanonischen Extrakten.
