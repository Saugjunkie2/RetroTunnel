1) ZWECK
================================================================================

Dieses Dokument definiert die Single Source of Truth (SoT) für jede
Informationsdomäne im System. Es beantwortet:

  - WO lebt die kanonische Wahrheit für einen Datenpunkt?
  - WER darf schreiben?
  - WAS passiert wenn die Wahrheit nicht verfügbar ist?
  - WIE werden Policy-Parameter aufgelöst?
  - WELCHE Namensregeln gelten?

2) SOT-MAP (Was ist Source of Truth für was?)
================================================================================

Grundsatz (MUST): Für jede finalisierte Informationsdomäne gibt es genau
EINE SoT. Keine geteilte Wahrheit, keine Inferenz aus anderen Quellen.
Domänen die noch OPEN/TBD sind, sind von dieser Regel ausgenommen bis
zur Finalisierung. OPEN-Domänen sind in der Tabelle explizit markiert.

  DNS-Enforcement            nftables DNAT53 Regeln        Runtime
  Derived Policy             Berechnet (kein DB-Feld)      Runtime

2.2) SoT-Hierarchie: SQL → Kernel

  SQL (Persistent)        ist die PRIMÄRE Wahrheit.
  Kernel (Runtime)        ist die ABGELEITETE Wahrheit.

  Wenn SQL und Kernel sich widersprechen, gewinnt SQL.
  Der Reconcile-Mechanismus (FLUSH+REBUILD) repariert Kernel-Drift
  periodisch aus SQL-Wahrheit.

  Richtung: SQL → Policy-Apply/Reconcile → Kernel (nftables/tc)
  Niemals:  Kernel → SQL (Kernel schreibt nicht zurück in SQL)

  Ausnahme: radacct (RADIUS Accounting) schreibt in SQL, wird aber
  von einem Daemon (FreeRADIUS) befüllt, nicht vom Kernel direkt.

2.3) DB-Down Verhalten (übernommen aus B052)

  Wenn die Datenbank nicht erreichbar ist:
  - FAIL-CLOSED für neue Verbindungen (kein Auth ohne DB)
  - Bestehende Sessions laufen weiter (Kernel-State bleibt)
  - Kein Reconcile möglich (nächster Zyklus wartet)
  - Settings-Resolution: key_state=DB_UNKNOWN → fail_class greift
  - Panel: Fehlermeldung, kein Login möglich

3) SQL-FIRST GRUNDREGELN
================================================================================

Übernahme aus B057 (vollständig, kanonisch):

SF-01  SQL ist SoT für Policy-Parameter.
       Keine "Magic Numbers" / implizite Defaults im Code.
       Code ist nur Enforcement-Engine; Policy kommt aus SQL.

SF-02  Kein Consumer darf stille Defaults verwenden.
       Jede Stelle, die einen Wert braucht, referenziert die SoT (SQL).
       Lokale Fallbacks sind VERBOTEN (außer failsafe_hardcap per Katalog).

SF-03  Missing/Invalid dürfen nie "Allow by accident" erzeugen.
       Fail-Class (FAIL_CLOSED / FAIL_SAFE_HARDCAP) ist maschinenlesbar
       im settings_catalog definiert.

SF-04  Deterministisch + debugbar.
       Jede effektive Policy ist reproduzierbar und /diag-fähig.
       Effective Value + Source + State müssen traceable sein.

SF-05  Driftarm.
       Overrides nur dort möglich, wo der Katalog explizit erlaubt
       (allowed_override_scope Whitelist). Verbotene Overrides → Hard Fail.

SF-06  Kein "Hidden Config File" für Settings-gesteuerte Policy.
       Es gibt keinen Schreibpfad außerhalb des Settings-Contracts
       für settings-gesteuerte Parameter (Keys in settings_catalog).
       HINWEIS: Nicht alle policy-relevanten Werte sind Settings-Keys.
       tunnel_type, access_role, ip_slot und derived_policy leben in
       ihren eigenen SoT-Domänen (DOMAIN_MODEL / NETWORK_MODEL), nicht
       im Settings-System.

4) SETTINGS-RESOLUTION (Effective Value Algorithmus)
================================================================================

Übernahme aus B057 §13.3, kanonisch:

4.1) Resolution Order (MUST)

  Priorität (höchste zuerst):
    1. settings_connection  (vpn_connection_id, key)
    2. settings_customer    (customer_id, key)
    3. settings_global      (key)
    4. Fallback gemäß fail_class (wenn kein Wert vorhanden/valide)

  Der ERSTE vorhandene und VALIDE Wert gewinnt.

4.2) Effective-Value Output (MUST)

  Jeder Consumer bekommt für jeden Key:
    effective_value      Der aufgelöste Wert
    effective_source     CONNECTION | CUSTOMER | GLOBAL |
                         FAILSAFE_HARDCAP | FAIL_CLOSED
    key_state            OK | MISSING | INVALID | FALLBACK_ACTIVE | DB_UNKNOWN
    reason_code          Maschinenlesbarer Grund (aus Reason-Registry)

  Consumers konsumieren NUR effective_* und key_state, nie raw SQL rows.

4.3) Missing vs Invalid (MUST)

  MISSING: Kein Eintrag vorhanden (für den betrachteten Scope).
  INVALID: Eintrag vorhanden, aber Typ/Range/Validator verletzt den Katalog.

  Reaktion pro Key ist im settings_catalog normiert:

  fail_class=FAIL_CLOSED:
    Missing → Hard Fail (Gate bleibt zu, Operation scheitert)
    Invalid → Hard Fail + Audit-Event + Health Flag

  fail_class=FAIL_SAFE_HARDCAP:
    Missing → failsafe_value (extrem restriktiver Notwert) + Warning
    Invalid → failsafe_value + Audit-Event + Health Flag
    MUSS:    failsafe_value darf nur VERSCHÄRFEN (tighten-only)
             policy_direction=TIGHTEN_ONLY ist Voraussetzung

  REGEL (MUST): Invalid ist HÄRTER als Missing (Policy Corruption).
  Invalid erzeugt IMMER ein Audit-Event (ratelimited) + Health Flag.

4.4) Observability-Pflichten (MUST)

  Wenn irgendein Key im Zustand MISSING/INVALID/FALLBACK_ACTIVE ist:
  - Admin-Panel: Health Warnings (read-only) mit betroffenen Keys
  - /diag: warnings inkl. betroffene Keys + effective_source + reason
  - Logs: Event ist ratelimited (kein Log-DoS)
  - Kein "stiller Notbetrieb" — Fallback darf nie unbemerkt bleiben

4.5) settings_catalog (maschinenlesbarer Contract, MUST)

  Pro Key definiert der Katalog:
    key                    String, immutable, unique global
    value_type             INT | FLOAT | BOOL | STRING | DURATION | CIDR | ENUM | JSON
    scope_default          GLOBAL (Default-Wert stammt aus global)
    allowed_override_scope NONE | CUSTOMER | CONNECTION | BOTH
    is_required            BOOL (MUST-Key ja/nein)
    range_min / range_max  Nullable, type-konsistent
    fail_class             FAIL_CLOSED | FAIL_SAFE_HARDCAP
    policy_direction       TIGHTEN_ONLY | RELAXES_ACCESS
    failsafe_value         Typed (nur bei FAIL_SAFE_HARDCAP)
    missing_behavior       Kanonischer Pfad (aus §4.3)
    invalid_behavior       Kanonischer Pfad (aus §4.3)
    description            Admin-facing Text
    docs_anchor            Referenz in Kanon

4.6) Override-Policy (MUST, Whitelist-basiert)

  OV-01  allowed_override_scope=NONE:
         Nur GLOBAL darf existieren. CUSTOMER/CONNECTION sind verboten.
  OV-02  allowed_override_scope=CUSTOMER:
         CUSTOMER darf existieren. CONNECTION ist verboten.
  OV-03  allowed_override_scope=CONNECTION:
         CONNECTION darf existieren. CUSTOMER ist verboten (außer BOTH).
  OV-04  allowed_override_scope=BOTH:
         CUSTOMER und CONNECTION sind erlaubt.
  OV-05  Override für nicht-overridebaren Key → Hard Fail + Audit.
  OV-06  Scope-Mismatch → Hard Fail + Audit.

5) SQL-NAMING-KONVENTIONEN
================================================================================

Übernahme aus NORM-02 (sql-first Entwurf), kanonisch für RetroTunnel:

5.1) Key-Format (MUST)

  NM-01  Canonical Settings-Keys sind lower_snake_case (a-z0-9_).
  NM-02  UPPERCASE Keys sind VERBOTEN als echte DB-Keys.
         Wenn UPPERCASE in älteren Textstellen vorkommt, gilt es als
         Alias/Alt-Notation und muss auf Canonical gemappt werden.
  NM-03  Jeder Key MUSS genau einem Prefix zuordenbar sein.

5.2) Erlaubte Prefixe (MUST)

  Namespace-Prefixe für Policy-Keys:
    vpn_       VPN-bezogene Policy (Tunnel, Session, Enforcement)
    web_       Webpanel/Portal-bezogene Policy
    peak_      Peak-Mode (CPU-Overload) Policy
    radius_    FreeRADIUS-bezogene Policy

  Querschnitt-Prefixe:
    settings_  Meta/Resolver/Cache Verhalten
    log_       Logging/Retention/Aggregation Policy
    spool_     Spool/Queue/Buffer Policy

  NEUE Prefixe (RetroTunnel-spezifisch, falls nötig):
    wg_        WireGuard-spezifische Keys (Server-Config, Keepalive etc.)
               Bewusst wg_ statt awg_: WireGuard ist die Konstante,
               nicht der Fork-Name (Amnezia/etc.).

5.3) Alias-System (MUST)

  AL-01  Kein "Silent Rename" ohne Alias-Eintrag.
  AL-02  Alias-Tabelle enthält: old_key, new_key, status (active|deprecated|removed).
  AL-03  Status=removed → reject + reason (nicht still ignorieren).
  AL-04  Resolver liefert canonical_key + alias_used Flag.

  HINWEIS FÜR RETROTUNNEL:
  Da RetroTunnel ein Greenfield-Konzept ist (keine produktive Settings-DB
  zu migrieren), gibt es aktuell keine Legacy-Keys zum Aliasieren.
  Das Alias-System wird trotzdem vorgesehen, damit spätere Key-Renames
  sauber migriert werden können.

5.4) Tabellen- und Spalten-Naming (MUST)

  TN-01  Tabellennamen: lower_snake_case, Plural.
         Beispiele: customers, vpn_connections, settings_global,
         active_session_locks, settings_catalog

  TN-02  Spalten: lower_snake_case.
         Beispiele: customer_id, subaccount_login, tunnel_type,
         access_role, ip_slot, fixed_ip, op_status, restricted_at

  TN-03  Primary Key: immer "id" (BIGINT UNSIGNED AUTO_INCREMENT).

  TN-04  Foreign Keys: <referenzierte_tabelle_singular>_id.
         Beispiele: customer_id → customers.id,
                    vpn_connection_id → vpn_connections.id

  TN-05  Timestamps: lower_snake_case mit _at Suffix.
         Beispiele: created_at, updated_at, claimed_at, disabled_at,
         email_verified_at, revoked_at

  TN-06  Boolean/Status Flags: Beschreibendes Adjektiv + _enabled
         oder is_ Prefix. Beispiel: is_restoreable (reason_registry)

  TN-07  ENUM-Felder: Werte sind UPPER_SNAKE_CASE.
         Beispiele: LEGACY, MODERN, USER, VIP, MODERATOR, ADMIN,
         PREPROVISIONED, CLAIMED, DISABLED, FAIL_CLOSED, FAIL_SAFE_HARDCAP

6) WRITE-PATH CONTRACT (Wer darf was schreiben?)
================================================================================

Übernahme aus B057 §13.6 + §13.7, angepasst an RetroTunnel Rollen:

6.1) Settings Write-Auth (MUST)

  Akteur     GLOBAL   CUSTOMER   CONNECTION   Beschreibung
  ────────── ──────── ────────── ──────────── ──────────────────
  ADMIN      W!       W!         W!           Über Panel, auditpflichtig

  USER       R        R          R            Kein Settings-Write

6.2) Write-Semantik (MUST)

  WS-01  Upsert: INSERT ... ON DUPLICATE KEY UPDATE (MariaDB-Syntax).
         Keine "SELECT dann INSERT" ohne Lock.
         Semantik: "no duplicate rows, deterministic last-write".
  WS-02  Jeder Write erzeugt Audit (changed_by, updated_at, comment).
  WS-03  Kein Schreibpfad außerhalb dieses Contracts.
  WS-04  Write gegen allowed_override_scope → Hard Fail + Audit.

  access_role ist KEINE Settings-Override-Ebene. Rollen-Differenzen
  laufen über derived_policy (DOMAIN_MODEL) oder getrennte

10) TESTS / VALIDIERUNG (DoD)
================================================================================

T-TM-01: Settings Resolution Order
  - CONNECTION Override überschreibt CUSTOMER und GLOBAL.
  - CUSTOMER Override überschreibt GLOBAL.
  - Nachweis: 3 Scopes mit verschiedenen Werten, effective_value prüfen.

T-TM-02: Fail-Closed bei Missing MUST-Key
  - MUST-Key mit fail_class=FAIL_CLOSED fehlt in allen Scopes.
  - Erwartung: Operation scheitert deterministisch.

T-TM-03: Failsafe-Hardcap bei Missing
  - Key mit fail_class=FAIL_SAFE_HARDCAP fehlt.
  - Erwartung: failsafe_value wird verwendet + Health Warning.

T-TM-04: Invalid Value Handling
  - Key mit ungültigem Wert (außerhalb range_min/max).
  - Erwartung: fail_class greift + Audit-Event + Health Flag.

T-TM-05: Override-Whitelist
  - Override-Versuch für Key mit allowed_override_scope=NONE.
  - Erwartung: Hard Fail + Audit-Event.

T-TM-06: Naming Convention
  - Alle Keys in settings_catalog sind lower_snake_case.
  - Alle Keys haben einen gültigen Prefix.
  - Keine UPPERCASE Keys als echte DB-Keys.

T-TM-07: /diag Trace
  - /diag gibt für jeden abgefragten Key effective_value,
    effective_source und key_state aus.
  - Fallback-Situation zeigt FALLBACK_ACTIVE + Warning.

T-TM-08: DB-Down Verhalten
  - DB nicht erreichbar → key_state=DB_UNKNOWN → fail_class greift.
  - Keine neuen Auth-Requests werden akzeptiert.
