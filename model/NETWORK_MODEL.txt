================================================================================

Der Server hat drei Netzwerk-Schichten:

  WAN       ens18         Öffentliches Internet (1x IPv4 + 1x IPv6 GUA)
  LOOPBACK  lo            Service-IPs (interne Dienste, nicht routbar)

(10.77.x.x) und/oder ULA IPv6 (fd77:x:x:x::x). Internet-Egress läuft
über NAT (IPv4 MASQUERADE) und NAT66 (IPv6 MASQUERADE).

3) VPN-INTERFACES
================================================================================

3.1) LEGACY (L2TP/IPsec via accel-ppp)
  Interface-Typ:   pppX (ein Interface pro Client-Session)
  Beispiel:        ppp0, ppp1, ppp2, ...
  Erzeugt durch:   accel-ppp bei L2TP-Connect
  IPv4:            Ja (Client-IP aus Rollen-Pool)
  IPv6:            Nein (LEGACY ist IPv4-only)
  QoS:             tc direkt auf pppX möglich (dediziertes Interface pro Client)
  DNS-Enforcement: iifname "ppp*" → DNAT53
  Peer-Isolation:  iifname "ppp*" oifname "ppp*" → DROP
  Lebensdauer:     Existiert nur solange Session aktiv

3.2) MODERN (AmneziaWireGuard)
  Interface-Typ:   awg0 (EIN Interface für ALLE Modern-Clients)
  Erzeugt durch:   AmneziaWireGuard Daemon beim Start
  IPv4:            Ja (Client-IP aus Rollen-Pool, per AllowedIPs zugewiesen)
  IPv6:            Ja (ULA fd77:... aus Rollen-Pool)
  QoS:             tc auf awg0 betrifft ALLE Peers gemeinsam — per-Peer
                   Shaping erfordert nftables-Marking + tc-Klassen oder
                   alternative Mechanik (wird in BASE-30/MOD-03 spezifiziert)
  DNS-Enforcement: iifname "awg0" → DNAT53
  Peer-Isolation:  iifname "awg0" oifname "awg0" → DROP
  Lebensdauer:     Persistent (Interface existiert auch ohne aktive Peers)

WICHTIGER UNTERSCHIED:
  Legacy: 1 Interface pro Client → tc/QoS pro Interface trivial
  Modern: 1 Interface für alle → tc/QoS pro Peer braucht Zusatzlogik

PEER-ISOLATION (MUST, PI-01 — GLOBAL, TUNNELÜBERGREIFEND):
  Client-zu-Client Traffic ist GLOBAL verboten, unabhängig vom Tunnel-Typ.
  Das gilt für alle 4 Kombinationen:
    ppp*  → ppp*   (Legacy ↔ Legacy)     → DROP
    awg0  → awg0   (Modern ↔ Modern)     → DROP
    ppp*  → awg0   (Legacy → Modern)      → DROP
    awg0  → ppp*   (Modern → Legacy)      → DROP
  Einzige erlaubte Ziele für VPN-Clients: SERVICE_NET + WAN (via Forward).
  Keine Ausnahmen, keine Rollen-Sonderrechte.

5) IP-POOLS (pro access_role)
================================================================================

Grundregel: Pools werden nach access_role vergeben, NICHT nach tunnel_type.
Ein Admin mit einem XP-Gerät (Legacy) und einem Android (Modern) bekommt
beide IPs aus dem ADMIN-Pool. tunnel_type bestimmt nur das Protokoll.

5.1) Pool-Übersicht

  Pool        CIDR             Hosts  Reserv. Slots  Allokierbar  IPv6 Bereich         Rolle
  ─────────── ──────────────── ────── ────────────── ──────────── ──────────────────── ──────
  ADMIN       10.77.2.0/24      254   Slot 0, Slot 1  2..254 (253) fd77:0:0:2::/64     Admin
  MODERATOR   10.77.3.0/24      254   Slot 0, Slot 1  2..254 (253) fd77:0:0:3::/64     Mod
  VIP         10.77.4.0/22     1022   Slot 0, Slot 1  2..1022(1021)fd77:0:0:4::/64     VIP
  USER        10.77.16.0/20    4094   Slot 0, Slot 1  2..4094(4093)fd77:0:0:16::/64    User

  Legende:
    Hosts     = Gesamte IPv4-Hostkapazität des CIDR (ohne Netz-/Broadcastadresse)
    Reserv. Slots = Reservierte Slot-Nummern: Slot 0 = Netzadresse,
                    Slot 1 = Gateway/System-Anchor (nicht allokierbar,
                    IP-INV-02/IP-INV-03)
    Allokierbar = Slot-Bereich für Client-IPs (first..last + Anzahl)

  Reserviert (nicht als Pool nutzbar):
  SERVICE_NET 10.77.0.0/28        14    —       fd77:0:0:0::/64      Dienste
  10.77.1.0/24                   254    —       —                     FREI (Zukunft)
  10.77.8.0/21                  2046    —       —                     FREI (Zukunft)

5.2) Pool-Regeln (MUST)

  PR-01  KEIN POOL-SHARING: Jede access_role hat exklusiv eigene Bereiche.
         Eine IP gehört immer genau einer Rolle.

  PR-02  CIDR-ENFORCEMENT: nftables-Regeln nutzen CIDR-Ranges für
         Rollen-Enforcement. O(1), kein Sync, kein Drift.

  PR-03  IPv6 NUR FÜR MODERN: Clients mit tunnel_type=LEGACY bekommen
         KEINE IPv6-Adresse, auch wenn ihr Pool einen v6-Bereich hat.
         v6_addr_policy=NONE für LEGACY, v6_addr_policy=FIXED_SQL für MODERN.

  PR-04  SLOT-BASIERT: IPs werden nicht direkt vergeben, sondern über
         ip_slot (Ganzzahl). fixed_ip und fixed_ipv6 werden deterministisch
         aus ip_slot materialisiert. Details in DOMAIN_MODEL/TRUTH_MODEL.

  PR-05  STICKY: Einmal zugewiesene IPs ändern sich nur bei Rollenwechsel
         oder Revoke. Kein Random-Lease, kein DHCP-Style Rotation.

  PR-06  QUARANTÄNE: Entzogene/revoked IPs gehen für QUARANTINE_DAYS
         in Quarantäne bevor sie neu vergeben werden können.

  PR-07  TAIL-RESERVE: Jeder Pool reserviert die letzten N Slots als
         Notpuffer (Break-Glass). Nur ADMIN darf aus der Reserve allozieren.

5.3) Slot-zu-IP Ableitung (Konzept, Details in TRUTH_MODEL)

  Für jeden Pool gilt eine deterministische Formel:
    fixed_ip   = pool_base_v4 + ip_slot
    fixed_ipv6 = fd77:0:0:<role_prefix_v6_visual>::A:B
                 (A = drittes IPv4-Oktett, B = viertes IPv4-Oktett)
                 (nur wenn v6_addr_policy=FIXED_SQL)
                 (IPv6 VISUELLE KODIERUNG — Detail: MANIFEST §4.3)

  Beispiele:
    ADMIN Pool, ip_slot=5:
      fixed_ip   = 10.77.2.0 + 5 = 10.77.2.5
      fixed_ipv6 = fd77:0:0:2::2:5

    USER Pool, ip_slot=42:
      fixed_ip   = 10.77.16.0 + 42 = 10.77.16.42
      fixed_ipv6 = fd77:0:0:16::16:42 (nur WIREGUARD)

  Slot 0 ist reserviert (Netzadresse, nicht allokierbar).
  Slot 1 ist SYSTEM-RESERVED (Gateway-Anchor, NIEMALS allokierbar —
  auch nicht per Break-Glass. Die .1 jedes Pools ist systemreserviert).
  Allokierbare Client-Slots: 2 bis (Host-Kapazität des Pools).
  Break-Glass-Allokation nutzt die Tail-Reserve, nicht Slot 1.
  Maximaler Slot = Host-Kapazität (z.B. 254 bei /24, 4094 bei /20).
  Tail-Reserve (PR-07) reduziert die allokierbaren Slots zusätzlich.

6) IPv6-MODELL
================================================================================

6.1) Grundsatz
  - Alle VPN-Clients bekommen intern ULA-Adressen (fd77:...), KEINE GUA
  - IPv6-Egress läuft über NAT66/MASQUERADE: Source am WAN ist Server-GUA
  - Am WAN darf NIEMALS eine Client-ULA (fd77:...) als Source auftauchen

6.2) IPv6 pro tunnel_type
  - LEGACY (L2TP/PPP):   IPv6 = NEIN (v6_addr_policy=NONE)
    XP/Vista unterstützen kein IPv6 über PPP/L2TP
  - MODERN (AWG):         IPv6 = JA (v6_addr_policy=FIXED_SQL)
    Dualstack: Client bekommt IPv4 + IPv6 aus dem Rollen-Pool

6.3) IPv6 pro access_role
  Alle Rollen haben IPv6-Bereiche definiert (Abschnitt 5.1).
  Ob IPv6 tatsächlich zugewiesen wird, hängt NUR an tunnel_type:
  - ADMIN mit Legacy-Gerät: kein IPv6 (trotz fd77:0:0:2::/64 im Pool)
  - USER mit Modern-Gerät:  IPv6 aus fd77:0:0:16::/64

6.4) NAT66/MASQUERADE
  - nftables POSTROUTING: ip6 saddr fd77::/16 oifname ens18 → masquerade
  - Alle Client-ULA-Prefixe werden über die Server-WAN-GUA geroutet
  - Negative Guard: Kein ULA-Source am WAN (tcpdump Proof, wie im alten B310)

7.2) Restricted Mode (saddr ∈ restricted_v4/v6 Sets)

  ────────────────── ───────────── ──────────────────

  WAN-Forward:       ALLES         ✗ (kein Internet im Restricted Mode)

7.3) nftables Enforcement-Pattern

  Rollen-Enforcement (CIDR-Range, statisch):

    IPv4:
    ip saddr 10.77.2.0/24  → ADMIN  (alle Admin-Rechte)
    ip saddr 10.77.3.0/24  → MOD    (Moderator-Rechte)
    ip saddr 10.77.4.0/22  → VIP    (VIP-Rechte, kein Admin-Panel)
    ip saddr 10.77.16.0/20 → USER   (User-Rechte, plan-gebunden)

    IPv6 (visuelle Kodierung, nur WIREGUARD/Dualstack):
    ip6 saddr fd77:0:0:2::/64  → ADMIN
    ip6 saddr fd77:0:0:3::/64  → MOD
    ip6 saddr fd77:0:0:4::/64  → VIP
    ip6 saddr fd77:0:0:16::/64 → USER

    L2TP_IPSEC hat kein IPv6 (NA-05) — IPv6-Regeln greifen nur fuer
    WIREGUARD Connections. /64 deckt den gesamten visuell kodierten
    Hostteil ::A:B ab (A und B liegen vollstaendig in den unteren 64 Bit).

  Zustands-Enforcement (dynamische Sets):
    restricted_v4 / restricted_v6   → Walled Garden Allowlist
    connect_pending_v4/v6           → Connect-Gate (kein WAN vor Policy-Apply)
    banned_v4 / banned_v6           → Fail2ban Banset

  Reihenfolge in nftables:
    1. Banned-Check (frühester Drop)
    2. Connect-Pending-Check (kein WAN bis Apply)
    3. Restricted-Check (Walled Garden Allowlist)
    4. Rollen-basierte Regeln (ADMIN/MOD/VIP/USER Differenzierung)
    5. Forward-Regeln (Full-Tunnel, NAT)

8) DNS-ENFORCEMENT (DNAT53 + DoT/DoQ BLOCK)
================================================================================

8.1) DNAT53 (Port 53 Umleitung)
  Alle DNS-Anfragen von VPN-Clients werden auf SERVICE_DNS umgeleitet:

  IPv4:  iifname {"ppp*","awg0"} udp dport 53 → dnat to 10.77.0.1:53
         iifname {"ppp*","awg0"} tcp dport 53 → dnat to 10.77.0.1:53
  IPv6:  iifname {"ppp*","awg0"} udp dport 53 → dnat to fd77:0:0:0::1:53
         iifname {"ppp*","awg0"} tcp dport 53 → dnat to fd77:0:0:0::1:53

  Gilt für ALLE Rollen (USER, VIP, MODERATOR, ADMIN). Keine Ausnahmen.
  Gilt in ALLEN Zuständen (normal, restricted, pending).

  Nach DNAT ist dst=10.77.0.1:53 → Traffic geht in nft filter INPUT
  → Dort muss Port 53 erlaubt sein (Abschnitt 7).

  Server-eigene DNS (OUTPUT): NICHT betroffen. Server nutzt Google DNS
  (resolv.conf). AdGuard nutzt Unbound als Upstream.

8.2) DoT Blocking (Port 853 TCP)
  iifname {"ppp*","awg0"} tcp dport 853 → DROP

8.3) DoQ Blocking (Port 853 UDP)
  iifname {"ppp*","awg0"} udp dport 853 → DROP

8.4) DoH (Port 443)
  Kann nicht per Port geblockt werden (teilt sich Port 443 mit normalem
  HTTPS). Wird über AdGuard-Blocklisten gefiltert (bekannte DoH-Domains).

8.5) DNS-ARCHITEKTUR AUSNAHME (DNS-EX-01, BEWUSSTE ENTSCHEIDUNG)
  Server-OUTPUT ist NICHT Teil des Client-DNS-Enforcement-Pfads.

  Client-DNS-Pfad:    Client → DNAT53 → SERVICE_DNS (AdGuard) → Unbound
  Server-DNS-Pfad:    Server OUTPUT → resolv.conf → Google DNS (8.8.8.8)

  Begründung: Der Server braucht externe DNS-Auflösung für seinen eigenen
  Betrieb (apt, Let's Encrypt ACME, E-Mail-Versand). Dieser Traffic läuft
  über OUTPUT (nicht PREROUTING) und wird daher nicht von DNAT53 erfasst.
  Das ist kein Fehler, sondern bewusste Architektur.

  AdGuard nutzt Unbound (SERVICE_RESOLVER .2) als Upstream, nicht Google
  DNS direkt. Unbound wiederum nutzt die Root-Hints / rekursive Auflösung.

9) OFFENE PUNKTE (OPEN)
================================================================================

OPEN-NET-01: AWG WAN-Port
  Der UDP-Port für AmneziaWireGuard auf der WAN-Seite ist noch nicht
  festgelegt. Wird in BASE-30_TUNNEL_AWG entschieden.
  Typisch: 51820 (WG Default) oder ein Custom-Port (DPI-Umgehung).
  Impact: WAN-Exposure (Abschnitt 2), Firewall-Regeln (BASE-50).

OPEN-NET-02: AWG Interface-Name
  awg0 ist der angenommene Name. AmneziaWG könnte einen anderen Default
  verwenden. Wird in BASE-30_TUNNEL_AWG verifiziert und hier nachgezogen.

OPEN-NET-03: QoS auf awg0 (per-Peer Shaping)
  Ein WireGuard-Interface ist shared (alle Peers). Per-Peer tc/QoS
  erfordert Zusatzlogik (nftables-Marking, tc-Klassen, oder IFB).
  Wird in BASE-30_TUNNEL_AWG + MOD-03_QOS spezifiziert.

OPEN-NET-04: Moderator Service-Zugriffe
  Welche Service-IPs der Moderator zusätzlich erreichen darf (z.B.
  Teilzugriff auf AdGuard-UI?) ist noch nicht entschieden.
  Impact: Scope-Matrix (Abschnitt 7.1).
