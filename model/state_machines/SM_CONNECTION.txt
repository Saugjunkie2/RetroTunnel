1) ZWEI-EBENEN-MODELL
================================================================================

Das Connection-Lifecycle trennt zwei orthogonale Dimensionen:

  EBENE A — OWNERSHIP (abgeleitet, kein eigenes Feld)
    Beantwortet: "Wem gehört die Connection?"
    PREPROVISIONED := customer_id IS NULL  (nie geclaimt, ownerlos)
    CLAIMED        := customer_id IS NOT NULL (gehört einem Customer)

    PREPROVISIONED bedeutet "nie geclaimt", unabhängig vom operativen
    Zustand. Eine nie geclaimte DISABLED Connection ist immer noch
    PREPROVISIONED (ownerlos). Der Begriff stammt aus dem alten Konzept
    und beschreibt ausschließlich den Besitzstatus.

    Einmal CLAIMED = immer CLAIMED. customer_id und claimed_at dürfen
    nach dem Claim nie wieder NULL werden.

  EBENE B — OPERATIVER ZUSTAND (persistiert als op_status)
    Beantwortet: "Was kann die Connection gerade?"
    ACTIVE     = Full Tunnel, normal nutzbar
    RESTRICTED = Walled Garden, connectbar aber nur SERVICE_NET
    DISABLED   = Operativer Hard-Stop, kein Tunnel, kein Panel

  Die beiden Ebenen sind orthogonal. Alle 6 Kombinationen sind gültig:
    PREPROVISIONED + ACTIVE      (vorbereitete Connection, Grace läuft)
    PREPROVISIONED + RESTRICTED  (Grace abgelaufen, UNCLAIMED_OVERDUE)
    PREPROVISIONED + DISABLED    (Deadline abgelaufen oder Admin-Disable)
    CLAIMED + ACTIVE             (normaler Betrieb)
    CLAIMED + RESTRICTED         (Quota/Expiry/Plan/Pause/Manual)
    CLAIMED + DISABLED           (Customer-Delete/Abuse/Timeout)

2) ERSTELLUNGSWEGE
================================================================================

2.1) Weg A: Laptop-Provisioning (ADMIN erstellt bei Geräteeinrichtung)

  EINSCHRÄNKUNG: Nur für access_role USER, VIP, MODERATOR.
  access_role=ADMIN ist bei Weg A NICHT zulässig — ADMIN-Connections
  entstehen nur über Weg "Für User" (DOMAIN_MODEL §6.4) mit
  sofortiger customer_id-Bindung (ONB-13, R-08).

  Ergebnis:
    customer_id = NULL (→ Ownership: PREPROVISIONED)
    op_status = ACTIVE, op_reason_code = NULL
    claim_token_hash = gesetzt
    unclaimed_grace_until = NOW() + vpn_unclaimed_grace_days
    claim_deadline = created_at + vpn_claim_deadline_days
    ip_slot = alloziert bei INSERT (CSPRNG, aus access_role Pool)
    fixed_ip/fixed_ipv6 = materialisiert aus ip_slot (atomar)
    Bei Pool-Full: INSERT scheitert fail-closed (kein Halbzustand)

2.2) Weg B: Self-Service im Panel (Customer erstellt selbst)

  Vorbedingungen:
    - Customer.status = ACTIVE, Plan erlaubt Self-Service

  Ergebnis:
    customer_id = Customer.id (→ Ownership: CLAIMED)
    claimed_at = NOW()
    op_status = ACTIVE, op_reason_code = NULL
    claim_token_hash = NULL, unclaimed_grace_until = NULL, claim_deadline = NULL
    ip_slot = alloziert bei INSERT (CSPRNG, aus access_role Pool)
    fixed_ip/fixed_ipv6 = materialisiert aus ip_slot (atomar)
    Bei Pool-Full: INSERT scheitert fail-closed (kein Halbzustand)

================================================================================
3) OPERATIVE ZUSTÄNDE (op_status)
================================================================================

3.1) ACTIVE
  - VPN-Auth wird akzeptiert (RADIUS accept / WG-Auth accept)
  - Full Tunnel (Internet-Zugang)
  - Panel-Zugriff grundsätzlich möglich, sofern per-Connection
    Panel-Login-Policy dies erlaubt (OPEN-SM-01)
  - op_reason_code = NULL
  - restricted_at = NULL, disabled_at = NULL

3.2) RESTRICTED
  - VPN-Auth wird akzeptiert (Tunnel kommt hoch)
  - NUR Walled Garden (SERVICE_NET: Panel, DNS, NTP)
  - Kein Internet, kein WAN-Forward
  - Hard-Cut bei Eintritt (Conntrack-Flush)
  - Panel-Zugriff grundsätzlich möglich (Self-Heal), sofern
    Panel-Login-Policy dies erlaubt (OPEN-SM-01)
  - op_reason_code = RESTRICT_* (NOT NULL, aus reason_registry)

3.3) DISABLED
  - VPN-Auth wird abgelehnt (RADIUS reject / WG-Auth reject)
  - Kein Tunnel, kein Walled Garden, kein Panel über diese Connection
  - Operativer Hard-Stop. Hard-Cut bei Eintritt (Session-Kill)
  - op_reason_code = DISABLE_* (NOT NULL, aus reason_registry)
  - Ggf. Restore-Fenster (reason-abhängig)
  - Danach: Revocation → Quarantäne → Pool-Rückführung

4.1) Übersicht

  ID    Von         Nach         Trigger                    Akteur
  ───── ─────────── ──────────── ────────────────────────── ──────────
  T-01  ACTIVE      ACTIVE       Claim (Ownership-Wechsel)  USER(REQ)
        RESTRICTED  ACTIVE       Claim + Unrestrict
  T-02  ACTIVE      RESTRICTED   Grace abgelaufen           JOB
  T-03  ACTIVE      RESTRICTED   Quota/Expiry/Plan/Pause    SYSTEM/ADMIN/CUST
  T-04  ACTIVE      DISABLED     Disable (reason-param.)    ADMIN/CUST
  T-05  RESTRICTED  ACTIVE|RESTR Restricted Re-Evaluation   ADMIN/CUST/SYSTEM
                                 (policy-re-eval bestimmt Ziel)
  T-06  RESTRICTED  DISABLED     Restrict-Timeout (Auto)    JOB
  T-07  RESTRICTED  DISABLED     Disable (reason-param.)    ADMIN/CUST
  T-08  DISABLED    ACTIVE|RESTR Admin Restore (policy-eval) ADMIN
  T-09  ACTIVE      ACTIVE       Rollenwechsel (in-place)   ADMIN
        RESTRICTED  RESTRICTED   Customer-Kaskade (D002 §7, D003-E02)
        DISABLED    DISABLED     access_role + ip_slot Mutation

  WICHTIG: T-04 und T-07 sind REASON-PARAMETRISIERT. Der op_reason_code
  bestimmt die Effekte (Restore-Fenster, Revocation-Timing etc.), nicht
  die Transitions-ID. Siehe Abschnitt 4.5/4.8.

4.2) T-01: Claim (Ownership: PREPROVISIONED → CLAIMED)

  Vorbedingungen (MUST):
    - customer_id IS NULL (PREPROVISIONED)
    - op_status IN (ACTIVE, RESTRICTED)
    - Customer.status = ACTIVE (email_verified_at IS NOT NULL)
    - claim_token_hash Match
    - Claim-IP-Autorisierung (B155)
    - NOW() < claim_deadline

  Effekte (atomar):
    - customer_id = Customer.id
    - claimed_at = NOW()
    - Falls op_status=RESTRICTED wegen UNCLAIMED_OVERDUE:
      op_status → ACTIVE, op_reason_code → NULL,
      restricted_at → NULL, restrict_finalize_at → NULL

  Race-Schutz: Row-Lock (SELECT ... FOR UPDATE)
  Lifecycle-Log: Event CLAIM

4.3) T-02: Grace abgelaufen (ACTIVE → RESTRICTED)

  Vorbedingungen:
    - customer_id IS NULL, op_status = ACTIVE
    - NOW() > unclaimed_grace_until

  Effekte (atomar):
    - op_status = RESTRICTED
    - op_reason_code = RESTRICT_UNCLAIMED_OVERDUE
    - restricted_at = NOW()
    - restrict_finalize_at = NOW() + default_restrict_window_days
    - Hard-Cut (Conntrack-Flush)
    - Lifecycle-Log: Event STATUS_CHANGE

4.4) T-03: Policy-Triggered Restrict (ACTIVE → RESTRICTED)

  Vorbedingungen:
    - op_status = ACTIVE
    - Trigger-Grund liegt vor
    - access_role ≠ ADMIN (R-08: ADMIN ist nicht restricted-fähig)

  Effekte (atomar):
    - op_status = RESTRICTED
    - op_reason_code = RESTRICT_* (höchstpriorer aktiver Grund)
    - restricted_at = NOW()
    - restrict_finalize_at = NOW() + default_restrict_window_days
      (aus reason_registry; NULL wenn Reason keine Auto-Finalisierung hat)
    - Source-Fact Verdrahtung (je nach Trigger):
      CUSTOMER_PAUSED:     customer_paused_at = NOW()
      ADMIN_MANUAL:        admin_manual_restricted_at = NOW()
      (Alle anderen Gründe: kein Source-Fact-Feld, da berechnet)
    - Hard-Cut (Conntrack-Flush)
    - Lifecycle-Log: Event STATUS_CHANGE

4.5) T-04: Disable aus ACTIVE (ACTIVE → DISABLED, reason-parametrisiert)

  Vorbedingungen:
    - op_status = ACTIVE
    - Gültiger DISABLE_* Reason

  Effekte (atomar, REASON-ABHÄNGIG):
    - op_status = DISABLED
    - op_reason_code = <DISABLE_*> (vom Aufrufer bestimmt)
    - disabled_at = NOW()
    - customer_paused_at = NULL, admin_manual_restricted_at = NULL
      (Source Facts löschen, auch wenn aus ACTIVE kommend normalerweise
       bereits NULL — explizit für Konsistenz)
    - Hard-Cut (Session-Kill)
    - Lifecycle-Log: Event STATUS_CHANGE

  Reason-abhängige Effekte (aus reason_registry):

    revocation_mode=IMMEDIATE (z.B. DISABLE_ADMIN_ABUSE):
      restore_until = NULL
      revoked_at = NOW()
      quarantine_until = NOW() + vpn_quarantine_days (materialisiert)

    revocation_mode=AFTER_RESTORE_WINDOW (z.B. DISABLE_CUSTOMER_SUSPENDED,
      DISABLE_ADMIN_MANUAL):
      restore_until = NOW() + default_restore_window_days
      revoked_at = NULL (wird erst nach Fristablauf durch Job gesetzt)
      quarantine_until = NULL

    revocation_mode=MANUAL_ONLY:
      restore_until = NULL
      revoked_at = NULL
      quarantine_until = NULL
      (Revocation nur per expliziter Admin-Aktion)

4.6) T-05: Restricted Re-Evaluation (RESTRICTED → ACTIVE oder RESTRICTED)

  Vorbedingungen:
    - op_status = RESTRICTED
    - Ein Restrict-Grund wurde behoben oder ein neuer ist hinzugekommen

  Effekte (atomar):
    - Reconcile re-evaluiert ALLE aktiven Bedingungen (INV-27)
    - Source-Fact Verdrahtung (Löschung bei Akteur-Aktion):
      Customer Reaktivieren: customer_paused_at = NULL
      Admin hebt Manual Restrict auf: admin_manual_restricted_at = NULL
    - KANONISCHE EINGANGSMENGE für aktive Restrict-Gründe:
      Die Gesamtmenge der aktuell gültigen RESTRICT-Bedingungen wird
      durch den Policy-Evaluator bestimmt (BASE-80_POLICY_APPLY_CORE).
      Dieser liest aus folgenden kanonischen Quellen:
        Quota-Stand       → vpn_connections + Accounting-Deltas
        Expiry            → vpn_connections.expiry_date vs NOW()
        Plan-Limits       → Plan-Engine (MOD-10_PLANS)
        Customer-Pause    → customer_paused_at IS NOT NULL (Source Fact)
        Admin-Manual      → admin_manual_restricted_at IS NOT NULL (Source Fact)
        Unclaimed-Overdue → customer_id IS NULL + unclaimed_grace_until
      Der Evaluator gibt eine geordnete Liste aktiver Gründe zurück.
      Reconcile wählt den höchstprioren (niedrigster precedence_rank).
    - Wenn KEIN Grund mehr aktiv:
      op_status = ACTIVE, op_reason_code = NULL
      restricted_at = NULL, restrict_finalize_at = NULL
    - Wenn ein ANDERER Grund noch aktiv:
      op_reason_code = nächsthöchster Grund (Precedence §5.3)
      restrict_finalize_at wird ggf. neu materialisiert
    - HARD-CUT UND LOGGING NUR BEI DELTA:
      Wenn die Re-Evaluation ein Delta erzeugt (Status- oder Reason-
      Wechsel): Hard-Cut (Conntrack-Flush) + Lifecycle-Log STATUS_CHANGE.
      Wenn KEIN Delta (identische Eingaben, identisches Ergebnis):
      KEIN Hard-Cut, KEIN Lifecycle-Log, KEINE Schreiboperation.
      (INV-31: Idempotenz gilt für den gesamten Effekt, nicht nur DB.)

4.7) T-06: JOB-Timeout (RESTRICTED → DISABLED, Auto-/Deadline-Disable)

  T-06 ist der kanonische JOB-initiierte Timeout-Pfad aus RESTRICTED.
  Er deckt ZWEI unabhängige Trigger ab:

  TRIGGER A: restrict_finalize_at Timeout (Auto-Finalisierung)
    Vorbedingung: restrict_finalize_at IS NOT NULL AND
                  NOW() >= restrict_finalize_at
    Reason: auto_finalize_to_reason_code (aus reason_registry)

  TRIGGER B: claim_deadline Timeout (SM_ONBOARDING §5.2)
    Vorbedingung: customer_id IS NULL AND NOW() >= claim_deadline
                  AND op_status = RESTRICTED
    Reason: DISABLE_UNCLAIMED_TIMEOUT (direkt)
    [v1.5: Trigger B ergänzt — claim_deadline aus RESTRICTED nutzt
     T-06 als JOB-Timeout-Pfad, nicht T-07 (Admin-Pfad)]

  Gemeinsame Vorbedingung:
    - op_status = RESTRICTED

  Effekte (atomar, für beide Trigger identisch):
    - op_status = DISABLED
    - op_reason_code = (trigger-abhängig, siehe oben)
    - disabled_at = NOW()
    - restricted_at = NULL, restrict_finalize_at = NULL
    - customer_paused_at = NULL, admin_manual_restricted_at = NULL
      (Source Facts löschen per INV-32, auch im Job-Pfad)
    - Reason-abhängige Effekte (basierend auf dem neuen
      DISABLE_*-Reason und dessen revocation_mode, wie T-04)
    - Hard-Cut (Session-Kill)
    - Lifecycle-Log: Event STATUS_CHANGE

4.8) T-07: Disable aus RESTRICTED (RESTRICTED → DISABLED, reason-param.)

  Vorbedingungen:
    - op_status = RESTRICTED
    - Gültiger DISABLE_* Reason

  Effekte (atomar):
    - Wie T-04, aber zusätzlich:
    - restricted_at = NULL, restrict_finalize_at = NULL (aufräumen)
    - customer_paused_at = NULL (Source Fact löschen)
    - admin_manual_restricted_at = NULL (Source Fact löschen)
    - Rest identisch zu T-04 (reason-abhängige Effekte)

  REGEL: Source Facts werden bei Eintritt in DISABLED IMMER gelöscht.
  Begründung: DISABLED = operativ tot. Nach eventuellem Restore (T-08)
  startet die Connection ohne alte Source Facts; der Zielzustand wird
  durch die Policy-Re-Evaluation bestimmt (ACTIVE oder RESTRICTED).
  Will der Customer danach wieder pausieren → neue Pause-Aktion nötig.

4.9) T-08: Admin Restore (DISABLED → ACTIVE | RESTRICTED)

  Vorbedingungen (MUST, alle gleichzeitig):
    - op_status = DISABLED
    - reason_registry.is_restoreable = true
    - restore_until IS NOT NULL AND NOW() < restore_until
    - revoked_at IS NULL (Revocation hat noch nicht begonnen)
    - ADMIN-Aktion im Panel

  Effekte (atomar):
    - disabled_at = NULL
    - restore_until = NULL
    - customer_paused_at bleibt NULL (wurde bei T-04/T-07 gelöscht)
    - admin_manual_restricted_at bleibt NULL (dto.)
    - POLICY-RE-EVALUATION (MUST):
      Nach Löschung der Disable-Felder wird der Policy-Evaluator
      (BASE-80) sofort ausgeführt. Dieser prüft alle berechneten
      Restrict-Gründe (Quota, Expiry, Plan-Limit, Unclaimed-Overdue):
      a) Kein berechneter Grund aktiv:
         op_status = ACTIVE, op_reason_code = NULL
      b) Berechneter Grund aktiv (z.B. Quota noch erschöpft):
         op_status = RESTRICTED, op_reason_code = höchstpriorer Grund
         restricted_at = NOW(), restrict_finalize_at materialisiert
      Restore ist KEIN Bypass aktueller Policy-Realität.
    - Lifecycle-Log: Event RESTORE (actor=ADMIN, Zielstatus dokumentiert)

  NICHT ERLAUBT wenn:
    - Reason ist nicht restorebar (z.B. DISABLE_ADMIN_ABUSE)
    - restore_until abgelaufen
    - revoked_at bereits gesetzt

4.10) T-09: Rollenwechsel — in-place Mutation (D002, Customer-Kaskade)

  Vorbedingungen:
    - customer_id IS NOT NULL (CLAIMED)
    - ADMIN ändert access_role des CUSTOMERS auf neue Rolle
    - ALLE Connections des Customers durchlaufen T-09 (D003-E02)
    - op_status kann ACTIVE, RESTRICTED oder DISABLED sein

  GEMEINSAME Effekte (atomar, EINE Transaktion über alle Connections):
    - access_role = NEUE Rolle
    - ip_slot = NEU (aus Pool der neuen Rolle)
    - fixed_ip = NEU (materialisiert aus neuem ip_slot)
    - fixed_ipv6 = NEU (materialisiert, falls v6_addr_policy != NONE)
    - Lifecycle-Log: Event ROLE_CHANGE
      (old_role, new_role, old_ip, new_ip, actor=ADMIN)

  SUBPFAD A — Connection ist ACTIVE:
    - op_status bleibt ACTIVE (kein Statuswechsel)
    - Hard-Cut (Session-Kill, erzwingt Reconnect)
    - Config-Versand bei MODERN (siehe unten)

  SUBPFAD B — Connection ist RESTRICTED:
    - op_status bleibt RESTRICTED (Restrict-Grund bleibt bestehen)
    - op_reason_code bleibt unverändert
    - restrict_finalize_at bleibt unverändert
    - Hard-Cut (Session-Kill, erzwingt Reconnect)
    - Config-Versand bei MODERN (siehe unten)
    (D002 §7.3: "Werden wie ACTIVE behandelt")

  SUBPFAD C — Connection ist DISABLED:
    - op_status bleibt DISABLED
    - access_role + ip_slot werden trotzdem geändert (D003-E02
      Constraint: alle Connections erben Customer-Rang)
    - KEIN Hard-Cut (keine aktive Session)
    - KEIN Config-Versand (Connection ist deaktiviert)
    (D002 §7.3)

  LEGACY-spezifisch:
    - subaccount_login: GLEICH (übernommen, kein neuer Login)
    - subaccount_nt_hash: GLEICH (übernommen)
    - Kundensicht: Reconnect → neue IP automatisch → fertig
    - KEIN E-Mail-Versand nötig, KEIN Profil-Änderung nötig

  MODERN-spezifisch:
    - wg_public_key: GLEICH (Key identifiziert Gerät, nicht Rolle)
    - Neue AllowedIPs → neue Config nötig
    - Aktualisierte Config per E-Mail an verifizierte Kunden-E-Mail
    - Key-Rotation nur bei explizitem Security-Ereignis, NICHT bei
      Rollenwechsel

  Fail-Closed: Pool-Full → gesamte Transaktion Rollback,
  alter Zustand bleibt erhalten.

  KASKADE (D003-E02, D002 §7): T-09 wird nicht einzeln ausgelöst,
  sondern als Teil einer Customer-Rollenänderung. ALLE Connections
  des Customers durchlaufen T-09 in EINER atomaren Transaktion.
  Siehe D002 §7 für Kaskade-Logik, Pool-/Budget-Prüfung.

5.1) Schema: Siehe DOMAIN_MODEL §7A.

5.2) Kanonische Reason-Codes

  RESTRICT-Codes (op_status=RESTRICTED):

  Code                          Finalisiert zu              Window
  ───────────────────────────── ─────────────────────────── ──────
  RESTRICT_UNCLAIMED_OVERDUE    DISABLE_UNCLAIMED_TIMEOUT   Settings
  RESTRICT_QUOTA_EXHAUSTED      DISABLE_QUOTA_TIMEOUT       Settings
  RESTRICT_EXPIRY_PASSED        DISABLE_EXPIRY_TIMEOUT      Settings
  RESTRICT_PLAN_LIMIT_EXCEEDED  DISABLE_PLAN_LIMIT_TIMEOUT  Settings
  RESTRICT_CUSTOMER_PAUSED      (keine Auto-Finalisierung)  NULL
  RESTRICT_ADMIN_MANUAL         (keine Auto-Finalisierung)  NULL

  KLARSTELLUNG RESTRICT_ADMIN_MANUAL (R-08):
    "ADMIN" im Code-Namen = der AKTEUR (Admin der restrictet),
    NICHT das Ziel. Ein Admin restrictet eine USER/VIP/MOD Connection.
    ADMIN-Connections selbst können NICHT restricted werden (R-08).
    Not-Aus für kompromittierte Admin-Connections = DISABLE (IMMEDIATE).
    Vorbedingung T-02: access_role ≠ ADMIN verhindert Anwendung auf ADMIN.

  DISABLE-Codes (op_status=DISABLED):

  Code                          Restorebar  Revocation-Mode
  ───────────────────────────── ─────────── ──────────────────
  DISABLE_UNCLAIMED_TIMEOUT     Nein        IMMEDIATE
  DISABLE_QUOTA_TIMEOUT         Nein        IMMEDIATE
  DISABLE_EXPIRY_TIMEOUT        Nein        IMMEDIATE
  DISABLE_PLAN_LIMIT_TIMEOUT    Nein        IMMEDIATE
  DISABLE_CUSTOMER_SUSPENDED    Ja          AFTER_RESTORE_WINDOW
  DISABLE_ADMIN_MANUAL          Ja          AFTER_RESTORE_WINDOW
  DISABLE_ADMIN_ABUSE           Nein        IMMEDIATE

  (DISABLE_ROLE_CHANGE entfällt — Rollenwechsel ist in-place
  Mutation per D002, kein DISABLE-Event mehr.)

  ENTFALLENE CODES:
  DISABLE_CUSTOMER_DELETE existiert NICHT. Löschen ist keine
  Deaktivierung sondern eine eigene Operation (→ §5.4 DELETE).
  Gelöschte Connections haben keinen DISABLE-Reason.

  HINWEIS: RESTRICT_CUSTOMER_PAUSED und RESTRICT_ADMIN_MANUAL haben
  KEINE Auto-Finalisierung. Sie bleiben RESTRICTED bis explizite
  Reaktivierung oder manuelles Disable.

5.3) Multi-Reason Precedence (F-001 Fix)

  Problem: Mehrere RESTRICT-Gründe können gleichzeitig gelten (z.B.
  Quota erschöpft UND Expiry abgelaufen). op_reason_code ist ein
  einzelnes Feld. Es braucht eine deterministische Auswahlregel.

  PRECEDENCE-REGEL (MUST):
  Wenn mehrere RESTRICT-Gründe gleichzeitig gelten, wird der Grund
  mit der HÖCHSTEN Priorität als op_reason_code gespeichert.

  Prioritätsreihenfolge (höchste zuerst):
    1. RESTRICT_ADMIN_MANUAL        (Admin hat explizit restricted)
    2. RESTRICT_UNCLAIMED_OVERDUE   (nie geclaimt, Grace abgelaufen)
    3. RESTRICT_PLAN_LIMIT_EXCEEDED (Plan-Downgrade)
    4. RESTRICT_EXPIRY_PASSED       (Laufzeit abgelaufen)
    5. RESTRICT_QUOTA_EXHAUSTED     (Datenvolumen erschöpft)
    6. RESTRICT_CUSTOMER_PAUSED     (Customer hat deaktiviert)

  SoT FÜR PRECEDENCE: reason_registry.precedence_rank (INT, NOT NULL).
  Die obige Textliste ist illustrativ. Im Betrieb entscheidet
  ausschließlich der niedrigste precedence_rank-Wert (1 = höchste
  Priorität). Neue RESTRICT-Codes MÜSSEN einen eindeutigen
  precedence_rank erhalten.

  RECONCILE-REGEL (MUST):
  T-05 (Restricted Re-Evaluation) setzt NICHT blind op_status=ACTIVE.
  Stattdessen: Reconcile re-evaluiert ALLE aktiven Bedingungen.
  Wenn nach Wegfall eines Grundes ein anderer Grund noch aktiv ist,
  bleibt op_status=RESTRICTED mit dem nächsthöchsten Reason.

  Beispiel:
    Connection ist RESTRICTED wegen QUOTA + EXPIRY.
    op_reason_code = RESTRICT_EXPIRY_PASSED (Prio 4 > Prio 5)
    Admin erneuert Quota → QUOTA fällt weg.
    Reconcile prüft: EXPIRY ist noch aktiv → bleibt RESTRICTED.
    Admin verlängert Expiry → EXPIRY fällt weg.
    Reconcile prüft: Keine Gründe mehr → op_status=ACTIVE.

  INVARIANTE:
  INV-26  op_reason_code bei RESTRICTED ist immer der höchstpriore
          aktuell gültige Grund gemäß Precedence-Reihenfolge.
  INV-27  T-05 darf op_status=ACTIVE nur setzen wenn KEIN
          RESTRICT-Grund mehr aktiv ist (Reconcile-Ergebnis).

5.4) Unabhängige Restrict-Quellen (F-001 v0.7 Fix)

  PROBLEM: op_reason_code ist der ausgewählte höchstpriore Grund,
  nicht die vollständige Menge aller aktiven Gründe. Wenn ein
  niedrigpriorer aktorgetriebener Grund (CUSTOMER_PAUSED, ADMIN_MANUAL)
  durch einen höherprioren Grund verdrängt wird, geht die
  Quellinformation verloren.

  LÖSUNG: Aktorgetriebene Restrict-Quellen werden als eigene
  persistente Source Facts auf vpn_connections geführt, getrennt
  vom aktuellen op_reason_code:

    customer_paused_at          TIMESTAMP, NULL
      Gesetzt wenn Customer "Deaktivieren" klickt.
      Gelöscht wenn Customer "Reaktivieren" klickt.
      Unabhängig von op_reason_code.

    admin_manual_restricted_at  TIMESTAMP, NULL
      Gesetzt wenn Admin eine Connection manuell restricted.
      ("admin" = AKTEUR, nicht Ziel. ADMIN-Connections selbst
      sind nicht restricted-fähig, siehe R-08. Not-Aus für
      kompromittierte Admin-Connections = DISABLE (IMMEDIATE).)
      Gelöscht wenn Admin die Restriction aufhebt.
      Unabhängig von op_reason_code.

  BERECHNETE Restrict-Quellen (keine eigenen Felder nötig):
    UNCLAIMED_OVERDUE:   customer_id IS NULL AND NOW() > unclaimed_grace_until
    QUOTA_EXHAUSTED:     Quota-Stand aus Accounting (berechnet)
    EXPIRY_PASSED:       expiry_date < NOW() (berechnet)
    PLAN_LIMIT_EXCEEDED: Plan-Engine Ergebnis (berechnet)

  POLICY-EVALUATOR-VERTRAG:
  Der Policy-Evaluator (BASE-80) sammelt ALLE sechs Quellen:
    1. customer_paused_at IS NOT NULL → RESTRICT_CUSTOMER_PAUSED aktiv
    2. admin_manual_restricted_at IS NOT NULL → RESTRICT_ADMIN_MANUAL aktiv
    3. customer_id IS NULL AND NOW()>grace → RESTRICT_UNCLAIMED_OVERDUE aktiv
    4. Quota erschöpft → RESTRICT_QUOTA_EXHAUSTED aktiv
    5. Expiry abgelaufen → RESTRICT_EXPIRY_PASSED aktiv
    6. Plan-Limit überschritten → RESTRICT_PLAN_LIMIT_EXCEEDED aktiv
  Aus der Menge aktiver Gründe wählt er den mit niedrigstem
  precedence_rank und schreibt diesen als op_reason_code.

  INVARIANTEN:
  INV-28  customer_paused_at: Setzen nur Customer, Löschen Customer ODER Lifecycle (INV-32)
  INV-29  admin_manual_restricted_at: Setzen nur Admin, Löschen Admin ODER Lifecycle (INV-32)
  INV-30  op_reason_code ist IMMER der höchstpriore aus der aktuellen
          Gesamtmenge aktiver Gründe (keine veralteten Werte).

5.5) RESTRICTED→RESTRICTED Reason-Re-Evaluation (F-002 v0.7 Fix)

  PROBLEM: Eine Connection kann bereits RESTRICTED sein, und ein neuer
  höherpriorer Grund tritt hinzu (oder ein Grund fällt weg, aber ein
  anderer bleibt). Das ist kein Statuswechsel, aber ein Reason-Wechsel.

  REGEL: Reconcile/Policy-Evaluator führt bei jeder Evaluation eine
  vollständige Re-Evaluation durch, unabhängig davon ob op_status sich
  ändert oder gleich bleibt.

  Wenn op_status=RESTRICTED und die Re-Evaluation ergibt:
    a) Höherpriorer Grund ist neu aktiv:
       - op_reason_code wird auf den neuen höchstprioren Grund gesetzt
       - restrict_finalize_at wird ggf. NEU materialisiert
         (aus dem neuen Reason, nicht dem alten)
       - Lifecycle-Log: Event STATUS_CHANGE (mit old/new reason)

    b) Aktueller Grund fällt weg, aber anderer bleibt:
       - op_reason_code wechselt zum nächsthöchsten aktiven Grund
       - restrict_finalize_at wird ggf. neu materialisiert
       - Lifecycle-Log: Event STATUS_CHANGE (Reason-Wechsel)

    c) Alle Gründe fallen weg:
       - op_status → ACTIVE, op_reason_code → NULL (T-05)

    d) Gleicher Grund bleibt, keine Änderung:
       - Keine Schreiboperation (Idempotenz)

  Beispiel:
    1. Connection ist RESTRICTED, op_reason_code=RESTRICT_QUOTA_EXHAUSTED
    2. Admin setzt admin_manual_restricted_at (manueller Restrict)
    3. Policy-Evaluator: QUOTA(Prio 5) + ADMIN_MANUAL(Prio 1) aktiv
    4. op_reason_code → RESTRICT_ADMIN_MANUAL (Prio 1 gewinnt)
    5. restrict_finalize_at → NULL (ADMIN_MANUAL hat keine Auto-Final.)
    6. Admin hebt manuellen Restrict auf (admin_manual_restricted_at=NULL)
    7. Policy-Evaluator: nur QUOTA(Prio 5) noch aktiv
    8. op_reason_code → RESTRICT_QUOTA_EXHAUSTED
    9. restrict_finalize_at → neu materialisiert

  INVARIANTE:
  INV-31  Reason-Re-Evaluation ist idempotent: mehrfaches Ausführen
          mit gleichen Eingaben erzeugt denselben Endzustand.

5.6) DELETE — Verbindung löschen (KEINE Deaktivierung)

  DELETE ist eine eigene Operation, KEIN DISABLE-Variant.
  Löschen ≠ Deaktivieren. Die Unterschiede:

  DISABLE:                          DELETE:
  - Credentials bleiben erhalten    - Credentials werden VERNICHTET
  - IP bleibt zugeordnet            - IP geht ins Recycling
  - Kann restored werden            - KEIN Restore möglich
  - op_status = DISABLED            - op_status = DELETED (terminal)
  - Reason-Code in reason_registry  - Kein Reason-Code nötig

  DELETE-Ablauf:
  1. Auth-Material wird vernichtet:
     LEGACY: subaccount_login + subaccount_nt_hash gelöscht
             (Row in vpn_connection_legacy_auth entfernt)
     MODERN: wg_public_key + wg_preshared_key gelöscht
             (Row in wg_connection_auth entfernt)
  2. IP-Adresse wird für Recycling freigegeben
  3. Connection-Row bleibt im System (Soft-Delete):
     op_status = DELETED, deleted_at = NOW()
     Nur noch für forensische/Log-Zwecke verfügbar
  4. Aktive Session wird beendet (Hard-Kill wenn online)

  DELETE-Auslöser:
  - User löscht eigene Connection im Panel
  - Admin löscht Connection
  - Customer wird DELETED → alle Connections werden DELETED

  SCHUTZ: LETZTE-AKTIVE-CONNECTION-REGEL (INV-35)
  Wenn ein Customer nur noch EINE Connection mit op_status=ACTIVE
  hat, kann diese Connection NICHT gelöscht und NICHT deaktiviert
  werden (durch User-Aktion). Verhindert Selbstaussperrung.
  Admin-Aktionen (DISABLE_ADMIN_ABUSE) sind von diesem Schutz
  AUSGENOMMEN — Missbrauch muss immer stoppbar sein.

6) RECYCLING-KETTE (DISABLED → Revocation → Quarantäne → Pool)
================================================================================

6.1) Revocation-Modi: Siehe Sektion 4.5 (T-04, reason-abhängig).

6.2) Restore-Fenster (nur bei AFTER_RESTORE_WINDOW)
  - restore_until = disabled_at + default_restore_window_days
  - Innerhalb: Admin kann Connection wiederherstellen (T-08)
  - Nach Ablauf: Job setzt revoked_at + quarantine_until

6.3) Quarantäne
  - quarantine_until = revoked_at + vpn_quarantine_days (materialisiert)
  - Während Quarantäne: Slot/IP nicht neu vergebbar

6.4) Pool-Rückführung
  - Nach NOW() >= quarantine_until: Slot für den Allocator freigegeben
  - Kein physisches DELETE des Connection-Datensatzes
  - Lifecycle-Log: Event POOL_RETURN

6.5) IP-Slot Retention bei historischen Connections (F-002 Fix)

  ENTSCHEIDUNG: ip_slot BLEIBT auf der alten Row (historischer Snapshot).

  Begründung:
  - Forensik/Haftung: "Welcher Account hatte IP x.x.x.x am Datum Y?"
    muss ohne Lifecycle-Log beantworbar sein (direkter SQL-Query).
  - Slot-Eindeutigkeit wird über den AKTIVEN Zustand geregelt:
    Nur Connections mit op_status != DISABLED AND revoked_at IS NULL
    zählen als aktive Slot-Owner.
  - Der Allocator prüft bei Vergabe:
    ip_slot NOT IN (SELECT ip_slot FROM vpn_connections
      WHERE access_role = ? AND op_status != 'DISABLED'
      AND revoked_at IS NULL)
    AND ip_slot NOT IN (SELECT ip_slot FROM vpn_connections
      WHERE access_role = ? AND revoked_at IS NOT NULL
      AND quarantine_until > NOW())
  - Historische Rows (DISABLED + revoked + quarantine abgelaufen) stören
    den Allocator NICHT, da sie weder aktiv noch in Quarantäne sind.
