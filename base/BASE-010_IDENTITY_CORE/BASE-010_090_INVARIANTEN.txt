================================================================================
1) OWNERSHIP-INVARIANTEN
================================================================================

  INV-01  customer_id IS NOT NULL ↔ claimed_at IS NOT NULL
          (bidirektionale Konsistenz: Claim setzt BEIDE oder KEINES)
  INV-02  customer_id darf nach Claim nie wieder NULL werden (monotonic)
  INV-03  claimed_at darf nach Claim nie wieder NULL werden (monotonic)
  INV-04  PREPROVISIONED = customer_id IS NULL (abgeleitet, kein Feld)

================================================================================
2) STATUS-REASON KONSISTENZ
================================================================================

  INV-05  op_status=ACTIVE → op_reason_code IS NULL
  INV-06  op_status=RESTRICTED → op_reason_code IS NOT NULL
  INV-07  op_status=DISABLED → op_reason_code IS NOT NULL
  INV-08  op_status=RESTRICTED → vpn_reason_registry.allowed_op_status
          = RESTRICTED (FK-Enforcement)
  INV-09  op_status=DISABLED → vpn_reason_registry.allowed_op_status
          = DISABLED (FK-Enforcement)
  INV-10  Enforcement ueber vpn_reason_registry (FK), nicht ueber
          String-Prefixe. RESTRICT_/DISABLE_ Prefixe sind Lesbarkeits-
          konvention, NICHT Enforcement-Logik.

================================================================================
3) TIMESTAMP-KONSISTENZ
================================================================================

  INV-11  op_status=ACTIVE → restricted_at IS NULL AND disabled_at IS NULL
  INV-12  op_status=RESTRICTED → restricted_at IS NOT NULL
          AND disabled_at IS NULL
  INV-13  op_status=DISABLED → disabled_at IS NOT NULL
  INV-14  op_status != RESTRICTED → restrict_finalize_at IS NULL
  INV-15  Reason ohne Auto-Finalisierung → restrict_finalize_at IS NULL
  INV-16  is_restoreable=false → restore_until IS NULL
  INV-17  op_status != DISABLED → restore_until IS NULL

================================================================================
4) REVOCATION / QUARANTAENE KONSISTENZ
================================================================================

  INV-18  revoked_at IS NOT NULL → op_status=DISABLED
  INV-19  revoked_at IS NOT NULL → restore_until IS NULL
          (revozierte Connection hat kein Restore-Fenster mehr)
  INV-20  quarantine_until IS NOT NULL ↔ revoked_at IS NOT NULL
          (bidirektional: Quarantaene existiert NUR bei Revocation)
  INV-21  quarantine_until IS NOT NULL → quarantine_until > revoked_at

================================================================================
5) REVOCATION-MODE LIFECYCLE-REGELN (zeit-/jobabhaengig)
================================================================================

  Diese Regeln werden durch Jobs/Transitionen erzwungen, nicht durch
  DB-Constraints allein.

  LR-01  revocation_mode=IMMEDIATE + Eintritt in DISABLED
         → revoked_at UND quarantine_until MUESSEN im selben
           atomaren Write materialisiert werden
  LR-02  revocation_mode=AFTER_RESTORE_WINDOW + Eintritt in DISABLED
         → revoked_at IS NULL bis restore_until abgelaufen
         → Job setzt revoked_at + quarantine_until nach Fristablauf
  LR-03  revocation_mode=MANUAL_ONLY + DISABLED
         → Nur explizite Admin-Aktion darf revoked_at setzen
           (kein Job, kein Reconcile)

================================================================================
6) MULTI-REASON PRECEDENCE
================================================================================

  INV-22  op_reason_code bei RESTRICTED ist IMMER der hoechstpriore
          aktuell gueltige Grund gemaess vpn_reason_registry.
          precedence_rank (niedrigster Rank = hoechste Prioritaet)
  INV-23  T-05 (Re-Evaluation) darf op_status=ACTIVE nur setzen wenn
          KEIN RESTRICT-Grund mehr aktiv ist
  INV-24  Reason-Re-Evaluation ist idempotent: mehrfaches Ausfuehren
          mit gleichen Eingaben erzeugt denselben Endzustand

================================================================================
7) SOURCE FACTS
================================================================================

  INV-25  customer_paused_at: Setzen nur durch Customer-Aktion,
          Loeschen durch Customer ODER Lifecycle (INV-28)
  INV-26  admin_manual_restricted_at: Setzen nur durch Admin,
          Loeschen durch Admin ODER Lifecycle (INV-28)
  INV-27  Source Facts (customer_paused_at, admin_manual_restricted_at)
          bestimmen ob der jeweilige RESTRICT-Grund aktiv ist.
          Sie sind UNABHAENGIG von op_reason_code (der zeigt nur
          den hoechstprioren Grund, nicht alle aktiven).
  INV-28  Source Facts werden bei Eintritt in DISABLED (T-04/T-06/T-07)
          IMMER geloescht. Nach Restore (T-08) startet die Connection
          ohne alte Source Facts.

================================================================================
8) SLOT / IP INVARIANTEN
================================================================================

  INV-29  ip_slot bleibt auf der Row auch nach DISABLED/Revocation
          (historischer Snapshot, Forensik)
  INV-30  fixed_ip/fixed_ipv6 sind immutable im Normalbetrieb (VC-04).
          Mutation nur bei Rollenwechsel (neue Allokation).
  INV-31  IP-Pool wird aus access_role abgeleitet (NICHT tunnel_type)
  INV-32  Rollenwechsel erzeugt neue IP-Allokation. Alter Slot →
          Quarantaene (Reuse-Policy B064).

================================================================================
9) IDENTITY-INVARIANTEN
================================================================================

  INV-33  web_customers.email ist UNIQUE (DB-Constraint)
  INV-34  email_verified_at ist monotonic (nie zurueck auf NULL)
  INV-35  status=ACTIVE → email_verified_at IS NOT NULL
  INV-36  access_role Aenderung kaskadiert auf alle Connections (D003-E02)
  INV-37  connection_ref ist UNIQUE und immutable nach Erstellung
  INV-38  claim_deadline ist immutable (Hard-Stop, kein Extend)
  INV-39  tunnel_type ist immutable nach INSERT (VC-08)
  INV-40  Alle Connections eines Customers haben dieselbe access_role (INV-36)
  INV-41  plan_id nur bei access_role=USER (VIP/MOD/ADMIN: NULL)

  INV-43  WIREGUARD → genau 1 Row in wg_connection_auth,

14) CONNECTION-LIMITS (Zaehlregel)
================================================================================

  INV-63  Aktiv-Budget: ACTIVE + RESTRICTED zaehlen gegen
          max_active_connections (Policy-System).
          Gesamt-Budget: max_active + vpn_disabled_connection_buffer
          (Settings-Key). Alle nicht-terminal-revoked Connections
          MIT customer_id zaehlen gegen Gesamt.
          Ownerlose PREPROVISIONED zaehlen erst nach Claim.

================================================================================
15) LETZTE-AKTIVE-CONNECTION SCHUTZ
================================================================================

  INV-64  Wenn ein Customer nur noch EINE Connection mit
          op_status IN (ACTIVE, RESTRICTED) hat, kann diese NICHT
          geloescht und NICHT deaktiviert werden (User-Aktion).
          Begruendung: RESTRICTED ist tunnelbar UND panel-faehig.
          Deaktivierung der letzten panel-faehigen Connection
          wuerde Selbstaussperrung verursachen.
          Admin-Aktionen (DISABLE_ADMIN_ABUSE, DISABLE_SECURITY_
          COMPROMISE) sind ausgenommen.

16) CUSTOMER-STATUS → CONNECTION KONSISTENZ
================================================================================

  INV-65  web_customers.status=SUSPENDED → nach Reconcile darf KEINE
          CLAIMED Connection dieses Customers op_status ACTIVE oder
          RESTRICTED haben. Alle werden DISABLED
          (DISABLE_CUSTOMER_SUSPENDED).
  INV-66  web_customers.status=DELETED → alle CLAIMED Connections
          dieses Customers werden physisch geloescht. Connection-Rows,
          Auth-Kindtabellen-Rows und Credentials werden entfernt.
          Die Zuordnung (customer_id, connection_ref) bleibt als
          DELETED-Event in log_connection_lifecycle erhalten.
  INV-67  suspended_at IS NOT NULL ↔ status=SUSPENDED
  INV-68  deleted_at IS NOT NULL ↔ status=DELETED
  INV-69  deleted_at ist monotonic (einmal gesetzt, nie zurueck auf NULL).
          DELETED ist terminal — kein Rueckweg.

  OPEN-010-01: [CLOSED] DELETE-Semantik (Marco-Entscheidung 2026-04-18)
  Entscheidung:
  a) Physische Loeschung: Connection-Row + Auth-Kindtabellen-Rows
     werden physisch entfernt (CASCADE). Keine Anonymisierung,
     kein Soft-Delete, kein Archiv-Zwischenschritt.
  b) Historie bleibt: log_connection_lifecycle behaelt die
     DELETED-Events (Forensik, Zuordnungshistorie). radacct-
     Eintraege bleiben erhalten (Accounting-Pflicht).
  c) IP-Recycling sofort: ip_slot wird umgehend freigegeben und
     dem Recycling-/Quarantaene-Prozess zugefuehrt (B064-Muster).
     Keine verzoegerte Freigabe fuer DELETE.
  d) FK-Verhalten: CASCADE auf vpn_connection_l2tp_ipsec_auth und
     wg_connection_auth (1:1, gehen mit der Connection). vpn_sessions
     mit Referenz: SET NULL oder Retention (Detail BASE-070).
  Implementation: Loeschlogik lebt in BASE-010 (Identity-Owner).
  Jobs/Timer fuer Batch-DELETE ggf. in BASE-070 oder MOD-001.

17) CLAIM-/TOKEN-/DEADLINE KONSISTENZ
================================================================================

  INV-70  Weg A (Admin-Provisioning): customer_id IS NULL →
          claim_token_hash MUSS NOT NULL sein.
          unclaimed_grace_until MUSS gesetzt sein.
          claim_deadline MUSS gesetzt sein.
  INV-71  Weg B (Self-Service): customer_id IS NOT NULL ab INSERT →
          claim_token_hash, unclaimed_grace_until, claim_deadline
          sind konsistent NULL.
  INV-72  Nach erfolgreichem Claim: claim_token_hash wird auf NULL
          gesetzt (Token invalidiert). Ein geclaimter Datensatz
          darf keinen gueltigen Claim-Token mehr tragen.
  INV-73  unclaimed_grace_until <= claim_deadline (Grace endet immer
          vor oder mit dem Hard-Stop).
  INV-74  claim_deadline ist immutable (INV-38). unclaimed_grace_until
          kann durch ADMIN per Grace-Reset verlaengert werden, aber
          nie ueber claim_deadline hinaus.

21) IP-SLOT EXKLUSIVITAET (ChatGPT-Review, 2026-04-18)
================================================================================

  INV-79  fixed_ip und fixed_ipv6 sind UNIQUE (DB-Constraint).
          Keine zwei Connections duerfen dieselbe materialisierte
          IP haben. ip_slot allein ist NICHT UNIQUE-faehig weil
          verschiedene Pools (access_role) denselben Slot-Wert
          haben koennen (USER Slot 5 ≠ ADMIN Slot 5 — verschiedene
          IPs weil verschiedene Pool-Prefixe). Die Eindeutigkeit
          liegt auf der materialisierten IP, nicht auf dem Slot.
          NULL-Werte (unprovisioniert) sind von UNIQUE ausgenommen
          (MariaDB: mehrere NULLs in UNIQUE-Spalte erlaubt).
