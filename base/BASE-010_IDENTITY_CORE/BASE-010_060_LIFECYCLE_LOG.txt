BASE-010 — LIFECYCLE LOG (log_connection_lifecycle)
================================================================================
DATEI: BASE-010_060_LIFECYCLE_LOG.txt
STATUS: ACTIVE

ZWECK:
  Vollstaendiges Audit-Log aller Lifecycle-Events einer Connection.
  Scope: Gesamter Lifecycle, nicht nur op_status-Wechsel.
  Ersetzt disabled_by auf der Haupttabelle.

VORGAENGER: DOMAIN_MODEL §7B
  Tabellenname: log_connection_lifecycle (BASE-000 K-04)

================================================================================
2) EVENT-TYPEN
================================================================================

  STATUS_CHANGE          op_status Wechsel (T-01..T-09)
  CLAIM                  Connection einem Customer zugeordnet
  RESTORE                Admin-Restore aus DISABLED
  REVOCATION             Revocation gestartet
  QUARANTINE_END         Quarantaene abgelaufen
  POOL_RETURN            IP-Slot zurueck in Pool
  SLOT_CHANGE            IP-Slot geaendert (Rollenwechsel)
  ROLE_CHANGE            access_role geaendert (T-09)
  SESSION_START          VPN-Session gestartet
  SESSION_END            VPN-Session normal beendet
  SESSION_HARDCUT        VPN-Session per Hard-Cut beendet
  SESSION_JANITOR_CLOSE  Stale Session durch Janitor geschlossen
  SESSION_SIMUSE_REJECT  SimUse-Guard hat Login abgelehnt
  CONNECTION_DELETED     Connection physisch geloescht durch Janitor
                         nach Ablauf der Tombstone-Quarantaene
                         (INV-81e). MUSS vor dem physischen DELETE
                         geschrieben werden (INV-78).
                         Snapshot-Felder tragen Identitaet weiter.
  CUSTOMER_DELETED       Customer-Account physisch geloescht
                         (web_customers.status=DELETED Trigger).
                         Loest pro CLAIMED Connection ein
                         STATUS_CHANGE-Event aus (→DISABLED mit
                         Reason DISABLE_CUSTOMER_DELETED, INV-66).
                         CONNECTION_DELETED-Events folgen erst
                         nach Ablauf von quarantine_until durch
                         Janitor (INV-81e).

================================================================================
3) WRITE-PATH
================================================================================

  Nur SYSTEM schreibt in diese Tabelle. Kein ADMIN/USER Direct-Write.
  Events werden automatisch bei Lifecycle-Transitionen erzeugt.
  INSERT-only: Keine UPDATEs, keine DELETEs (Audit-Trail).

  FK-STRATEGIE BEI PHYSISCHER LOESCHUNG (OPEN-010-01 [REVISED] 2026-05-11):
    vpn_connection_id FK: ON DELETE SET NULL.
    Physische Loeschung erfolgt jetzt verzoegert: erst nach Tombstone-
    Phase durch Janitor (Ablauf von quarantine_until, INV-81e). Vor
    der physischen Loeschung wird CONNECTION_DELETED-Event geschrieben
    (INV-78). Beim DELETE der Connection-Row wird vpn_connection_id
    in allen vorhandenen Log-Rows auf NULL gesetzt, die Log-Rows
    bleiben erhalten.
    connection_ref (Snapshot) traegt die forensische Identitaet.
    customer_id (Snapshot) traegt die Customer-Zuordnung.
    → Tombstone-Phase: Connection-Row + Log-Rows existieren beide.
      Direkte Abfrage via JOIN auf vpn_connection_id moeglich.
    → Nach Janitor-DELETE: Log ist weiterhin auswertbar ueber
      connection_ref + customer_id Snapshots.
