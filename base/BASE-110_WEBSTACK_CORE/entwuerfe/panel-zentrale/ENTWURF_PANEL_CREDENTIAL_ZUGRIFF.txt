1) L2TP/IPSEC — CREDENTIAL-ZUGRIFF IM PANEL
================================================================================

  LOGIN-NAME (subaccount_login):
    User sieht seinen Login-Namen im Panel (read-only).
    Login-Name ist NICHT aenderbar durch den User.
    Begruendung (B155): "Name/Identity der Connection bleibt fix
    (kein Rename durch User)". Login-Name ist generiert, immutable,
    und Teil der RADIUS-Auth-Kette.
    Aenderung wuerde bedeuten: radcheck umschreiben, alle aktiven
    Sessions invalidieren, Forensik-Bruch.

  VPN-PASSWORT:
    User kann sein VPN-Passwort im Panel sehen (Button "Klartext
    anzeigen") und aendern.
    Passwort-Aenderung:
    - User gibt altes Passwort ein
    - User gibt neues Passwort 2x ein (Bestaetigung)
    - SYSTEM hasht neues Passwort (NT-Hash fuer MSCHAPv2)
    - SYSTEM schreibt neuen Hash in vpn_connection_l2tp_ipsec_auth
    - Alter Hash wird ueberschrieben (kein Klartext-SoT)
    - Lifecycle-Log: EVENT_TYPE=CREDENTIAL_ROTATE

  ADMIN-SICHT:
    Admin sieht Credential-Status (vorhanden ja/nein, wann rotiert).
    Admin sieht NICHT den Klartext oder den Hash.
    Admin kann "Passwort zuruecksetzen" triggern (generiert neues,
    sendet per Email an den User).

================================================================================
2) WIREGUARD — CREDENTIAL-ZUGRIFF IM PANEL
================================================================================

  CONFIG-DATEI:
    User sieht seine bestehende WireGuard-Config im Panel.
    User sieht seinen QR-Code (zur schnellen Einrichtung auf Mobilgeraeten).
    Config enthaelt: PrivateKey (Client), PublicKey (Server), Endpoint,
    AllowedIPs, DNS, PresharedKey (wenn gesetzt).

  NEUE CONFIG GENERIEREN:
    User kann eine neue Config generieren.
    Sicherheitsbestaetigung: User muss sein Panel-Login-Passwort eingeben.
    Danach:
    - SYSTEM generiert neues Keypair (Client PrivateKey + PublicKey)
    - SYSTEM aktualisiert wg_connection_auth (neuer PublicKey)
    - SYSTEM generiert neue Config-Datei
    - Config + Credentials werden per Email an den User gesendet
    - Email-Anhang: ZIP-Datei, geschuetzt mit dem Panel-Login-Passwort
      des Users (passwortgeschuetztes ZIP)
    - Lifecycle-Log: EVENT_TYPE=CREDENTIAL_ROTATE

  ADMIN-SICHT:
    Admin sieht Credential-Status (PublicKey vorhanden ja/nein,
    wann rotiert, PresharedKey vorhanden ja/nein).
    Admin sieht NICHT den PrivateKey (lebt nur im Config-Export).
    Admin sieht NICHT den PresharedKey (Secret).
    Admin kann "Config neu generieren" triggern.

================================================================================
3) SICHERHEITSMODELL (GRANT-Implikationen)
================================================================================

  Der User braucht Zugriff auf seine eigenen Credentials.
  Der Admin braucht KEINEN Zugriff auf Secrets.

  DB-LEVEL:
  webpanel_user braucht fuer L2TP/IPsec:
    SELECT auf subaccount_login (read-only, User-Anzeige)
    KEIN SELECT auf subaccount_nt_hash (Hash wird nie angezeigt)
    UPDATE auf subaccount_nt_hash (Passwort-Rotation)

  webpanel_user braucht fuer WireGuard:
    KEIN SELECT auf wg_preshared_key (Secret)
    SELECT auf wg_public_key NUR fuer Anzeige "vorhanden ja/nein"
    (idealerweise via redacted View: has_psk BOOLEAN, pk_present BOOLEAN)

  KLARSTELLUNG: User-Passwort-Aenderung laeuft ueber Panel-App
  (PHP). Panel-App ist SYSTEM-Komponente. "USER triggert → SYSTEM
  schreibt" gilt auch hier: User klickt Button, Panel-App validiert
  altes Passwort, Panel-App schreibt neuen Hash.

  OFFENER PUNKT: Exakte DB-Views/Projections → BASE-110_WEBSTACK_CORE.

4) DELETE-SEMANTIK (Marco-Entscheidung 2026-04-17)
================================================================================

  Connection "geloescht" bedeutet:
  - Connection-Row wird physisch entfernt (DELETE FROM vpn_connections)
  - Auth-Kindtabelle Row wird physisch entfernt
  - Zuordnung zum Webaccount (customer_id) bleibt fuer Historie
    erhalten → in log_connection_lifecycle als DELETED-Event
  - ip_slot geht in Quarantaene/Pool-Rueckfuehrung
  - Credentials werden vernichtet (kein Klartext, kein Hash bleibt)

  WAS FUER FORENSIK BLEIBT:
  - log_connection_lifecycle: Alle Events inkl. connection_ref,
    customer_id, IP-History (metadata JSON)
  - connection_ref als historischer Identifier in Logs
  - customer_id Referenz bleibt in Logs (nicht in vpn_connections)

  - Wie genau werden FKs behandelt? (cascade vs set null)
  - Retention fuer radacct (RADIUS Accounting)?

  - Anonymisierung statt physischer Loeschung als Alternative?
