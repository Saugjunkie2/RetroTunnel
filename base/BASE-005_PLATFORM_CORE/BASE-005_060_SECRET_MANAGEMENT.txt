2) ABLAGE-PRINZIPIEN
================================================================================

  PRINZIP 1: Secrets gehoeren in DB oder in geschuetzte Files.
             Nie in Code, nie in Git, nie in Logs.
  PRINZIP 2: File-Secrets haben Permissions 0600 und gehoeren dem
             berechtigten Dienst-User (siehe BASE-005_050 §3).
  PRINZIP 3: SQL-basierte Secrets durch DB-GRANTs geschuetzt
             (BASE-000 §2: RADIUS sieht kein wg_*).
  PRINZIP 4: Secrets erscheinen NIEMALS in:
             - Logs (File-Logs, Journal, Audit)
             - Diag-Output (/diag Endpoint)
             - Admin-UI (nur Placeholder "********")
             - Backups ohne Verschluesselung (falls entschieden)

================================================================================
3) BACKUP-UMGANG (Entscheidung Marco 2026-04-16, Claude+ChatGPT)
================================================================================

  VERSCHLUESSELUNG: GPG

  DB-Dumps und /etc/-Archive werden VOR Ablage auf Backup-Storage
  mit GPG verschluesselt. Begruendung: Ein Backup ist ein neuer
  Vertrauenskoerper. Sobald Dumps + /etc/ den Live-Host verlassen,
  reicht "Storage ist schon geschuetzt" allein nicht aus — gerade
  weil /etc/ echte Secrets enthaelt (IPsec PSK, WG PrivateKey,
  DB-Credentials, SMTP-Credentials).

  WAS WIRD VERSCHLUESSELT:
    - DB-Dump (retrotunnel_main_db komplett)
    - /etc/ Archiv (alle Dienst-Konfigurationen)

  RECOVERY-MINIMUM (was MUSS im Backup sein):
    - DB-Dump (alle Tabellen, alle Daten)
    - /etc/ (Konfigurationen aller Dienste)
    - WG Server PrivateKey (in /etc/wireguard/awg0.conf)
    - IPsec PSK (in /etc/ipsec.secrets)

  PFLICHTEN:
    - Restore-Drill als Pflicht (Restore muss praktisch geuebt sein)
    - Schluesselhaltung definieren: wo liegt der GPG-Key?
    - Verlustfall-Szenario: was passiert bei GPG-Key-Verlust?

4) ROTATION-PRINZIPIEN
================================================================================

  Secret-Typ              Rotierbar?   Trigger
  ----------------------- ------------ --------------------------
  Customer Password       Ja           User-Wunsch (Panel)
  WG Server PrivateKey    Theoretisch  Erzwingt neue Peer-Configs
  IPsec PSK               Theoretisch  Erzwingt Client-Reconfig
  RADIUS Shared Secret    Ja           Admin-Entscheidung
  SSH Host Keys           Ja           Admin-Entscheidung
  DB-User Passwoerter     Ja           Admin-Entscheidung

  ROTATION-REGEL: Neues Secret generieren UND altes invalidieren.
  Kein paralleler Betrieb (alte + neue Credentials gleichzeitig
  gueltig) — das waere ein Sicherheitsfenster.

5) SICHTBARKEIT VON SECRETS (differenziert)
================================================================================

  Secrets werden in ZWEI Klassen unterschieden:

  A) INFRASTRUKTUR-SECRETS (NIE im Klartext sichtbar):
     DB-User-Passwoerter, SSH-Keys, RADIUS Shared Secret,
     WG Server PrivateKey, SMTP-Credentials.
     Diese Secrets sind system-intern und haben im Panel,
     in Logs und im Diag-Output NICHTS im Klartext zu suchen.
     Anzeige: "********" oder "[geschuetzt]".

  B) CONNECTION-CREDENTIALS (Klartext im Panel PFLICHT):
     Login-Name, Passwort (L2TP), PSK-Anzeige, WireGuard-Config,
     WireGuard-Keys (inkl. PresharedKey), QR-Code.
     Diese Daten sind BETRIEBSDATEN die der User braucht um sein
     Geraet selbstaendig einzurichten. Kein Verstecken, kein
     Redaktieren. User sieht seine eigenen, Admin sieht alle.
     Einzige Ausnahme: subaccount_nt_hash (technisches Hash-
     Artefakt, nicht menschenlesbar — INV-75).
     (Marco-Entscheidung, bestaetigt ueber mehrere Sessions)

  LOGS UND DIAG-OUTPUT (R-12, gilt fuer BEIDE Klassen):
  Weder Infrastruktur-Secrets noch Connection-Credentials
  duerfen in Logs oder Diag-Output erscheinen.
  Sanitizing vor dem Schreiben ist Pflicht.

  BACKUPS:
  Hashes in DB-Dumps sind OK. Klartext-Secrets in Backups
  werden durch GPG-Verschluesselung geschuetzt (§3).
